# 07 - 日志详情命中明细设计

> **状态: 已实施**（2026-09-15 立项；2026-09-16 按当前工作区源码复核；2026-09-17 实施）。命中明细传递、序列化、UI 与持久化均已接通，并补齐条数/字节上限与截断标记、快照切片隔离与 op 层落库归一。规则数量与 MAC/USCC 已提交实现见 [02](02-规则引擎设计.md)。
> **决策变更（2026-09-17）**：已批准在日志命中明细中下发并展示命中原文 `original`（连同规则标签与占位符），供管理员在日志详情定位被脱敏的原文片段。此前「实施边界修订」中"不下发原文"的约束由本决策取代——原文仅为命中片段（非整份请求体），显式下发，可见性边界与日志详情/错误日志原有管理员可见性一致。命中明细超出条数/字节上限时仅截断展示摘要，并置 `mask_matches_truncated` 截断标记。
> **审计复核（2026-09）**：多代理审计再次列出「命中原文明文入库 error_logs」，经评审维持原决策——命中片段入库属预期行为，不修；有界归一（128 条 / 256B / 32KB）与既有管理员可见性边界不变。

## 一、需求目标

在日志详情中不仅显示"已脱敏"标记和占位符, 还展示本次请求命中了哪些脱敏规则, 通过占位符定位请求体中被替换的位置, 并展示被替换的命中原文片段。不改变请求转发和响应还原逻辑。

---

## 二、现状与关键发现

### 2.1 引擎已产出命中明细, 但未保存

脱敏引擎 `internal/relay/mask/engine.go` 的 `Apply` 返回结构化 `MaskResult`:

```go
type Match struct {
	Label       string // 规则标签, 如 PHONE / EMAIL / SECRET / TERM
	Original    string // 命中原文
	Placeholder string // 替换占位符, 如 {{PHONE_bcdfgh}}
}

type MaskResult struct {
	Masked  string   // 脱敏后的文本
	Mapping *Mapping // 本轮会话映射表(供还原用)
	Matches []Match  // 命中明细  ← 现由 applyRequestMask 返回并透传进 RequestState
}
```

当前 `mask_integration.go:applyRequestMask` 已直调 `mask.Engine.Apply`（不再经 `engine.go:ApplyBytes`），并返回 `res.Matches`，转发入口 `handler.go` 因而能拿到命中明细:

```go
masked, mapping, mErr := applyRequestMask(raw.Body, sessionKey, g.RelayConfig.MaskEnabled)
// ...
if maskMapping != nil {
	streamRestorer = mask.NewStreamRestorer(maskMapping)
	request.Masked = true   // 仅有布尔标记, 没有命中明细
}
request.updateBody(string(masked))
```

### 2.2 日志请求体已是占位符版本

成功执行脱敏后，`RequestState.updateBody` 把状态中的请求体替换为占位符版本，`/api/v1/log/:id/request-body`（`getRequestBody`）读取该状态。因此日志详情已有占位符，缺少规则与占位符的对应关系。此结论限于更新之后；初始状态创建早于脱敏，见第六节时序风险。

### 2.3 命中明细的现成形状

`/api/v1/mask/test` 管理接口(`internal/server/handlers/mask.go`)已返回命中明细（管理员主动提交样本的临时预览）。日志命中明细最初不复用该含原文形状、只下发 label+placeholder（2026-09-15 边界），2026-09-17 翻转后日志 DTO 也含 `original`（有界、受上限与截断标记约束），形状与预览相近但为独立 `MaskMatchSummary` 类型。现有预览结构如下:

```go
type maskTestMatch struct {
	Label       string `json:"label"`
	Original    string `json:"original"`
	Placeholder string `json:"placeholder"`
}
```

### 2.4 前端展示点

- 实时日志详情: `web-next/src/pages/Logs.tsx` 的 `TraceSheet`(约 L668), 头部"已脱敏"标记在 L817, 左侧"请求体"面板在 L833-861。
- 错误日志展开区: 同文件 `ErrorLogRow`(约 L580-638), 展示 `request_body` / `err_detail`。

### 2.5 持久化错误日志无命中记录

`model.ErrorLog`(`internal/model/error_log.go`)只保存脱敏后的 `RequestBody`, 无命中字段; `recordErrorLog`(`handler.go:1071`)入队时不带命中明细。

## 三、实施方案

### 3.1 后端: 命中明细进请求状态

1. 日志 `mask_matches` 元素现含 `label`、`original`、`placeholder`（DTO 与落库均含 original），受条数/字节上限与截断标记约束；后端在发布/入队前完成转换，不依赖前端隐藏。如后续增加 preview/sha256，须先明确脱敏方式。
2. `applyRequestMask` 已直调 `mask.Engine.Apply` 取得 `MaskResult` 并转换为日志 DTO（不再经 `ApplyBytes` 二选一）；不要额外扫描一次请求体，也不要遍历会话 `Mapping` 生成本请求明细。保留关闭/未命中返回 nil 映射的语义。
3. `RequestState` 增加可选的安全明细字段；通过持锁更新方法一次写入 `Masked`、脱敏 body 与明细后走 `publishRequestLocked`。同步检查快照复制路径，切片不可共享可变底层数组；避免日志流看到字段不同步。
4. **不变项**: 不把原始请求体写回 body; 不改变发往上游的内容; 空会话/请求级 mapping、跨轮占位符复用、`StreamRestorer` 逻辑保持。只使用本次 `Apply` 的 Matches，不混入历史映射。引擎按规则执行顺序、每条规则内唯一原文保序收集，并非全请求出现次数；预览接口另按占位符在文本中首次出现位置排序，日志首期保留引擎顺序。
5. 在编码前约定单请求条数、字段字节数与总字节数上限，并提供截断标记；超限只裁剪展示摘要，不改变实际脱敏与还原。`maxFinished=200` 仅限制已结束请求数量，不能代替载荷上限。

### 3.2 后端: 序列化与接口

1. 更新 `RequestState.MarshalJSON`(`internal/relay/state.go:192`)的自定义序列化路径, 把 `mask_matches` 纳入对外 JSON, 避免因自定义 marshal 遗漏新字段。
2. `/api/v1/log/:id/request-body` 保持返回脱敏后请求体不变; **不新增任何恢复明文的接口**, 命中明细随状态流下发而非挂在请求体接口上。
3. 持久化错误日志（第二阶段，可选，不阻塞实时日志首期）:
   - `model.ErrorLog` 可增加 `MaskMatches` TEXT 字段，仅存安全 DTO 的 JSON。API 须明确返回数组而非把 JSON 字符串冒充数组，补充解析与坏值降级。
   - `recordErrorLog` 在入队时携带安全摘要；`op/error_log.go` 的现有清洗只处理 `ErrBrief`/`ErrDetail`/`RequestBody`，不会自动保护新增字段，需补清洗与限额。
   - 新增列涉及 schema 升级：当前 `internal/db/db.go` 对 ErrorLog 使用 AutoMigrate，仍需验证旧库补列。历史 NULL/空串需显式归一为空列表，不回填历史明细，不能声称“无需迁移”。
   - `errCompleteLogCount` 是进程内按错误类累计完整请求体次数，前 3 条以外仅存摘要；建议明细仅随这前 3 条完整请求体保留，并另设字节上限。沿用错误日志保留天数、条数与删除策略。

### 3.3 前端: 日志详情展示

1. 前端 `RequestState` 类型(`web-next/src/lib/types.ts`) 已增加 `mask_matches?: MaskMatchSummary[]`，其中 `MaskMatchSummary = { label, original, placeholder }`；该展示类型为独立类型，不复用脱敏测试的 `MaskTestMatch`。
2. 在 `TraceSheet` 左侧"请求体"面板内增加"脱敏命中"区域:
   - 每条展示规则标签（含 MAC/USCC/未知标签兼容）、命中原文及占位符；按普通文本渲染。
   - 当前后端有 `masked` 但没有明细是正常现状；新增字段缺省或为空时不报错，不推断为配置变化。无命中不显示区域，截断时明确提示。
   - 命中原文仅为命中片段（非整份请求体），随日志详情/错误日志管理员可见性下发。
3. 请求体展示保持占位符版本；第二阶段启用错误日志持久化后，`ErrorLogRow` 再复用安全摘要组件。

### 3.4 实施顺序与验收清单（已实施）

顺序：安全 DTO/容量约定 → 单次引擎结果接通 → 持锁状态更新、序列化与快照 → 实时日志 UI → 首期验收 → 可选持久化及旧库升级验收。补充增量：命中明细裁剪与截断标记 → 状态快照切片隔离 → op 段落库归一 → 前端截断提示。

- [x] PHONE + TERM + MAC/USCC 等命中生成正确 label/placeholder；重复原文不按出现次数冒充命中条数；跨请求复用占位符但不携带历史明细。
- [x] 全局关闭、分组关闭、未命中、空请求及引擎失败路径不发布半成品明细；内置规则全关时自定义词行为不变。
- [x] `MarshalJSON`、首次快照、增量发布与重连快照字段一致；快照不受后续切片修改影响（`MaskMatches` 已 `slices.Clone`）；旧版本字段缺省可正常展示。
- [x] 转发上行 body、请求体接口、非流式/流式响应还原不因日志功能改变。
- [x] 命中原文仅以命中片段下发；条数/字节上限生效（128 条 / label 32B / original 256B / placeholder 64B / 总 32KB），超限置 `mask_matches_truncated`，截断不影响实际替换。
- [x] 持久化：旧库补列（AutoMigrate）、NULL/空串/坏 JSON 由 `normalizeMaskMatches` 归一、数组序列化、每类前 3 条配额、保留和删除策略均通过实现。

## 四、安全边界(凭据红线, 文档 04 §五)

| 项目 | 边界 |
|---|---|
| 日志下发范围 | 既有管理员鉴权仍保留；概览 SSE 会向所有订阅者下发状态（含命中原文片段），非仅已打开详情 |
| 上游请求 | 不变, 仍是占位符版本 |
| 请求体接口 | 仍返回脱敏后文本, 不新增明文恢复接口 |
| 错误日志落盘 | 存 `label + original + placeholder`，入队前清洗/限额；原文仅为命中片段，非整份请求体；命中明细已加条数/字节上限与截断标记，`normalizeMaskMatches` 归一兜底（坏 JSON/超限丢弃、不 redact 原文） |
| 会话映射表 | 仍为内存 + TTL，不落库、不借日志导出；摘要仍可关联请求，应受访问与留存限制 |
| preview/sha256 扩展 | 非首期必需；预览可能泄露片段、低熵值哈希可枚举，不能声称摘要天然不可还原 |

## 六、风险与对策

1. **敏感原文重新可见**: 命中原文按片段随明细显式下发（2026-09-17 决策翻转后的边界），受 128 条 / original 256 字符 / 总 32KB 上限，超限置 `mask_matches_truncated`；可见性边界与日志详情/错误日志原有管理员可见性一致。管理员鉴权与前端模糊不是替代措施。
2. **SSE 载荷与内存增大**: 不假设命中通常只有几十条；以明确条数/字节预算限制每请求摘要，并覆盖所有快照和发布路径。终态 `maxFinished=200` 裁剪不约束在途请求数。
3. **旧版本进程/旧记录兼容**: 字段缺省按可选处理；持久化新增列需升级验收，空串/NULL/损坏 JSON 由服务端归一，不让前端自行猜测。
4. **请求体暂存时序**: `state.go:newRequestState` 在脱敏前创建状态并发布，后续才由 `updateBody` 覆盖；命中明细按设计显式下发命中原文片段（受上限与截断标记约束），并非「不泄露原文」边界。请求体接口本身仍返回脱敏后占位符版本；若要提升为全时段保证（请求体接口所有时刻已是脱敏版本），应另补时序防护与并发读取验收。
