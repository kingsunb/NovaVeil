# 03 - 流式 SSE 增量还原设计

> **状态：已实现**（2026-09-10，REQ-015）。流式还原代码见 `internal/relay/mask/stream_restore.go`。本文档为设计参考。
> 本文档设计流式响应的占位符还原方案。这是整个脱敏功能**最难的部分**：
> 占位符可能被拆分到两个甚至多个 SSE event 中，必须缓冲拼接后才能完整匹配还原。
> 参考 maskit `engine/transparent.py` 的跨 chunk 缓冲拼接逻辑。

---

## 一、问题

模型流式返回（`text/event-stream`）时，每个 SSE event 只携带一小段增量文本。占位符 `{{PHONE_bcdfgh}}` 可能被拆成：

```
event 1: "建议 {{TERM_fnqtsw}} 核对 {{CONNSTR_zk"
event 2: "pmqx}} 的连通性"
```

如果逐 event 独立还原，event 1 里的 `{{CONNSTR_zk` 不完整，无法匹配，直接写出会导致客户端看到残缺占位符。

---

## 二、核心方案：增量还原器

### 2.1 状态机

```go
// internal/relay/mask/stream_restore.go
type StreamRestorer struct {
    mapping  *Mapping          // 占位符 → 原文 反向映射表
    pending  []byte            // 尾部待定缓冲：可能是不完整占位符的前缀
}
```

### 2.2 处理流程

每个 event 到达时调用 `Push(chunk []byte) []byte`，返回**可以立即写给客户端的已还原字节**：

```text
输入 chunk
  ↓
拼接：buffer = pending + chunk
  ↓
扫描 buffer 中的完整占位符 {{LABEL_xxxxxx}}
  ↓
找到完整占位符？
  ├─ 是：还原为原文，输出已还原部分
  │       尾部若存在「可能是占位符开头但未闭合」的残余 → 存入 pending
  └─ 否：检查 buffer 尾部是否有「{{」开头但未闭合
          ├─ 有：把这部分存入 pending，输出前面的明文
          └─ 无：全部输出，pending 清空
```

### 2.3 关键判断：尾部残余识别

从 buffer 末尾向前查找最后一个 `{{`，若其后没有对应的 `}}`，则从该 `{{` 起的部分是**可能不完整的占位符前缀**，须暂存 pending：

```go
func splitTail(buffer []byte) (output, pending []byte) {
    // 从末尾找最后一个 "{{"
    idx := bytes.LastIndex(buffer, []byte("{{"))
    if idx < 0 {
        return buffer, nil // 无占位符开头，全部输出
    }
    // 检查该 "{{" 之后是否有 "}}" 闭合
    if bytes.Contains(buffer[idx:], []byte("}}")) {
        return buffer, nil // 已闭合，全部输出
    }
    return buffer[:idx], buffer[idx:] // 未闭合部分暂存
}
```

### 2.4 安全边界

- **pending 上限**：占位符最长 `{{LABEL_6位}}` ≈ 20 字节。pending 超过 64 字节仍未闭合，说明不是占位符（可能是代码里的 `{{` 模板语法），直接刷出。
- **超时刷出**：pending 存留超过 N 个 event 仍未闭合，刷出避免无限缓冲。

## 三、协议适配

NovaVeil 支持 OpenAI / OpenAI Responses / Anthropic 三种协议，SSE event 结构不同：

| 协议 | 增量文本字段 | event 格式 |
|---|---|---|
| OpenAI Chat | `choices[0].delta.content` | `data: {...}\n\n` |
| OpenAI Responses | `output[].content[].text` | `data: {...}\n\n` |
| Anthropic | `content[].text`（`content_block_delta`） | `event: ...\ndata: {...}\n\n` |

### 复用 NovaVeil 现有 transformer
NovaVeil 的 `relay/protocol.go` 与 `looplj/axonhub/llm/transformer` 已有协议解析能力。
还原器**不自行解析 SSE**，而是复用 handler 现有逐 event 解码路径，在解码出的文本增量上做还原，再重新编码写回。

### 插入方式
```go
// handler.go 流式分支（约 771 行；文档 01 §3.2）
// 现有：event 已解码出本事件增量的 Data 文本；还原在「解码文本 → 还原 → 重新编码」层面
if streamRestorer != nil {
    event.Data = restoreStreamEvent(event.Data, format, streamRestorer)
}
sse.Encode(&encoded, sse.Event{Data: event.Data}) // 重新编码后写出
c.Writer.Write(encoded.Bytes())
c.Writer.Flush()
```

> 注意：`restoreStreamEvent` 按协议提取增量文本字段，`StreamRestorer.Push` 只处理解码出的文本增量（`event.Data`），再经 `sjson` 写回并重新编码；不在已编码的 SSE 帧字节上做字符串替换（会破坏帧结构）。该路径已实现。

## 四、中途无事件

maskit 的硬约束（`AGENTS.md` 第 4 条）：**中途无事件时返回空列表 `[]`，严禁返回 `b""` 导致 chunked 语法提前断连**。

NovaVeil 流式转发已有此语义（`upstream.go` 的 `events` 流），还原器须保持：
- `Push` 返回空内容时，handler 不写出、不 Flush，等待下一 event。
- 还原器绝不主动关闭流。

---

## 五、非流式 vs 流式对比

| | 非流式还原 | 流式还原 |
|---|---|---|
| 时机 | 完整响应 body 一次性还原 | 逐 event 增量还原 |
| 缓冲 | 无需 | 需要 pending 缓冲 |
| 占位符完整性 | 必然完整 | 可能跨 chunk 拆分 |
| 实现难度 | 小 | **大** |
| 代码位置 | `restore.go` | `stream_restore.go` |

## 六、测试要点

1. **占位符完整在单 event 内**：直接还原。
2. **占位符跨两个 event 拆分**：缓冲拼接后还原。
3. **占位符跨三个 event 拆分**：多级缓冲。
4. **`{{` 后无 `}}`（代码模板语法）**：不误判为占位符，刷出。
5. **连续多个占位符混合普通文本**：逐一还原。
6. **pending 超长刷出**：超过 64 字节强制刷出。
7. **流中途客户端断开**：pending 不泄漏，restorer 可 GC。
8. **空 event**：返回空，不写出，不断连。
