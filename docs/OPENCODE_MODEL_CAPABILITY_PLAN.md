# OpenCode 同步时带上能力，不带计价

> 状态：待实施。更新日期：2026-09-21。本文是实施计划，不是已落地行为。
> 当前事实：`internal/task/sync.go` 只把 `/v1/models` 的模型名写成 `ChannelModel`；`ChannelModelLimit` 只有管理员配置的 `max_output` 和 `thinking_level`，由 `applyChannelModelLimits` 写进上游请求。
> 与 [按模型协议计划](OPENCODE_NATIVE_PROTOCOL_PLAN.md) 共用同一次公开目录读取，但能力字段不决定协议，协议字段也不写入能力。两份计划可以分批落地；先落地的一方拥有这次 HTTP 读取，后落地的一方复用，不对同一目录打两次。

## 1. 问题

OpenCode 公开能力目录除了协议，还带每个模型的上下文窗口、推理、工具调用、结构化输出，以及输入/输出模态。NovaVeil 同步只保存模型名。控制台和评估无法区分一个模型是否支持工具或有多大上下文，调用方也只能猜。

这些事实不能塞进 `ModelLimits`。那一列的语义是「管理员要注入的请求限制」。目录里的输出上限一旦写入 `max_output`，同步就会开始改写真实请求的 `max_tokens`。计价更不能进来：目录或 models.dev 上的价格是别人的估算，不是 NovaVeil 的用量账。

## 2. 决定

只在 `OpencodeCompat` 渠道的模型行上保存一份只读能力快照。选路、故障转移、透传和计费都不读它。`applyChannelModelLimits` 不读它。

快照字段：

| 字段 | 含义 | 没有值时 |
|---|---|---|
| `context_window` | 目录给出的上下文 token 数 | 不写 0 冒充「无上下文」；字段省略 |
| `max_input` | 目录给出的输入上限 | 省略 |
| `max_output_hint` | 目录给出的输出上限，只展示 | 省略；绝不写入 `ModelLimits.MaxOutput` |
| `reasoning` | 目录标记支持推理 | 省略 |
| `tool_call` | 目录标记支持工具调用 | 省略 |
| `structured_output` | 目录标记支持结构化输出 | 省略 |
| `input_modalities` | 输入模态 | 省略，不写空数组表示「纯文本」 |
| `output_modalities` | 输出模态 | 同上 |

不保存价格、货币、缓存读写单价、计费单位。响应和日志里也不出现这些键。

能力按渠道模型保存。同一模型名在 OpenCode Free 与官方渠道上可以不同。非 OpenCode 渠道不读目录，模型行上也不出现这份快照。

## 3. 同步

触发条件与现有模型同步相同：渠道 `AutoSync` 为真，且 `OpencodeCompat` 为真。其他渠道的 `SyncModelsTask` 行为不变。

一次同步里的失败要分开：

- `/v1/models` 失败：保持今天的行为，不改模型名单，也不改能力。
- `/v1/models` 成功、目录失败或超时：模型名单仍按今天的规则增删；已有能力快照原样留下。目录失败不得把快照清成空。
- 两边都成功：auto 模型的快照在同一次 `ChannelUpdate` 里写上。`SyncModelsTask` 现在重建 auto 模型时只写名字和 `Source`，实施时必须把快照一并放进新行，否则每轮同步都会丢掉能力。
- 目录里没有该模型：保留上一次的快照。没有上一次就保持省略。不因此把模型从渠道里删掉，也不要因此拒绝转发。

`Source=manual` 的行不被 AutoSync 替换。目录里能对上名字时，可以只更新这份只读快照，不动名字、来源和 `ModelLimits`。对不上时留下管理员保存过的快照；手工模型默认没有快照。

出厂种子模型不在启动时访问目录。能力留空，直到管理员打开 AutoSync 或手动执行一次同步。不把上下文窗口写进 `BuiltinFreeChannels`。

目录 URL、档位划分和 SDK 判断若与协议计划是同一次响应解析，协议和能力从同一份解码结果取出。解析失败按目录失败处理，不使用说明文档的 Markdown 表格兜底，不访问 models.dev。

## 4. 展示

渠道编辑器只在 OpenCode 渠道的模型行上显示已有快照：上下文、推理、工具、结构化输出、模态。没有快照就显示「未知」，不要显示 0 或「不支持」。控件只读。保存渠道时前端把快照原样带回去，后端拒绝用模型保存接口改写它；管理员要改的是 `ModelLimits`，那条路径保持原样。

不在分组、评估排序或路由里消费这些字段。评估页可以稍后读同一份快照，本项不改评估逻辑。

## 5. 不做什么

- 不把 `max_output_hint` 或 `context_window` 写入请求体。
- 不根据能力隐藏模型、跳过渠道或改变故障转移顺序。
- 不接 models.dev，不在 `UsageBucket.Cost` 里用目录价格补缺。缺价时的手动单价是另一项。
- 不把能力放进 `ModelLimits`，不把协议放进能力快照。
- 不在自定义渠道上打开 `opencode_compat` 来换取能力同步。
- 不把目录响应、价格或模型提供方原文写进请求日志。

## 6. 实施顺序

1. 模型行增加能力快照的存储，迁移只加列或 JSON，不改现有 `model_limits`。
2. OpenCode 渠道同步时读公开目录并写快照。先确认与协议计划共用一次请求；本项单独落地时，协议字段保持不动。
3. 重建 auto 模型不丢快照；目录失败不删模型、不清快照。
4. 编辑器只读展示。保存请求若带了不同的快照，后端以库里的值为准并忽略该处输入。
5. 行为落地时另写 Agent Note。本文保持计划。

## 7. 验收

- OpenCode 渠道同步成功后，目录里有上下文和工具标记的模型，在模型行上能读到对应字段；`ModelLimits.MaxOutput` 与改动前相同。
- 同一模型名在两条 OpenCode 渠道上的快照互不影响。
- 目录超时或非 2xx 时，模型增删仍只看 `/v1/models`；已保存的快照还在。
- `/v1/models` 返回空且渠道已有 auto 模型时，仍然跳过删除，快照也不被清空。
- 非 OpenCode 渠道同步不发目录请求，模型行没有能力字段。
- 转发一个带了 `ModelLimits` 的 OpenCode 模型，请求体里的最大输出和思考等级只来自管理员配置，不来自快照。
- 响应 JSON、导出和日志里没有价格字段。
- 前端不能通过保存模型把快照改成另一个上下文窗口。
