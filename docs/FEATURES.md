## REQ-001 请求日志缓存 token 展示

### 背景

当前请求日志只显示「输入 token」与「输出 token」两类用量。部分上游（Anthropic、支持 prompt caching 的 OpenAI 兼容渠道等）会对输入做缓存，当请求命中缓存时，会额外产生「缓存读 token」（cache read tokens）。这类缓存 token 目前既未在日志中单独展示，也无法与「真实新增输入」区分。

### 需求描述

1. 请求日志的 token 用量，在现有「输入」「输出」之外，增加「缓存」维度，用于展示本次请求命中上游缓存的输入 token 数量。
2. 仅当请求命中缓存时才展示缓存 token；未命中缓存的请求（占多数）不展示缓存 token，避免产生噪音或误导。
3. 展示位置覆盖：
   - 请求日志列表的 token 用量列（与输入/输出并列）；
   - 请求追踪详情中的用量区域（与输入/输出并列）。

### 边界（不做）

- 不改变现有输入/输出 token 的展示行为。
- 不要求展示缓存写入（cache write）的分档细分，聚焦「命中缓存的读 token」。

## REQ-002 请求日志 key 名称展示

### 背景

每个请求由某个 API key 发起，key 具有独立的名称。当前请求链路已携带 key 名称信息，但请求日志（尤其是日志列表）未能直观展示每个请求来自哪个 key，不利于排查用量归属与问题定位。

### 需求描述

1. 请求日志需展示「发起该请求的 key 名称」。
2. 只展示名称即可（key 名称是唯一、可读的标识），不展示原始密钥。
3. 展示位置覆盖：
   - 请求日志列表（新增「key 名称」列）；
   - 错误日志列表（如当前未展示，需补上 key 名称）。

### 边界（不做）

- 不展示原始密钥本身，避免密钥泄露风险。

## REQ-003 渠道导入

### 背景

渠道管理页已支持「导出全部渠道」（纯文本格式，含渠道名、上游地址、全部明文密钥），但缺少对应的「导入」能力，无法用导出的文件批量恢复或迁移渠道。

### 需求描述

1. 在渠道管理页提供「导入」入口，与现有「导出」并列。
2. 支持选择此前通过「导出」生成的文件进行导入。
3. 导入与导出使用同一格式（每渠道一段：`# 渠道名`、上游地址、每行一把密钥、渠道间空行分隔），保证导出的文件可直接再次导入。
4. 导入后按文件内容批量创建渠道。
5. 展示导入结果反馈（如成功/失败的数量及原因）。

### 边界（不做）

- 导入恢复范围以导出文件实际包含的内容为准。模型清单、类型、分组、启用状态等未导出，导入时不做额外恢复或猜测。
- 渠道导入与设置页的「整库导出/导入」是两套独立能力，本需求不涉及整库导入。

### 现行实现

导出范围是缓存中的全部渠道，包括内置渠道和没有 Key 的渠道。页面上的搜索或筛选不影响导出。每段仍是 `# 渠道名`、明文上游地址、然后每行一把明文 Key；没有 Key 时只有名称和地址。空的密钥槽不写。内置渠道导入后会按自定义渠道创建，不会保留内置标记。

## REQ-004 用量数据保留时间与趋势档位扩展

### 背景

主页的「Token 用量趋势」与「模型用量 Top」均基于同一份按小时聚合的 token 用量数据（usage_buckets）。当前该数据永久保留、无清理机制；趋势图仅支持 24h / 7d / 30d 三档。

### 需求描述

1. 在设置页新增「用量数据保留时间」设置项，用于控制 Token 用量趋势与模型用量 Top 所依赖的用量历史数据的保留时长，默认「永久保留」。
2. 超过保留时长设定的历史用量数据将被清理，仅保留设置时长内的数据；选择「永久」时不清理。
3. 保留时间提供若干档位（至少覆盖 1 年、3 年、永久），默认永久。
4. Token 用量趋势的展示范围在现有 24h / 7d / 30d 基础上，新增「1 年」「3 年」「永久」档位；「永久」展示全部保留的历史数据。
5. 模型用量 Top 与总量统计受该保留时间约束：设置保留时长后，仅统计保留时长内的数据；选「永久」则维持全量统计。

### 边界（不做）

- 本需求仅针对 token 用量数据（usage_buckets）；错误日志、会话留存等其他数据的保留策略不受此设置影响。
- 不改变现有按小时聚合的用量写入粒度与方式。

## REQ-006 模型测试超时默认调整为 300 秒

### 背景

模型测试（channel_test）当前单次超时为 30 秒，覆盖单模型测试与逐密钥测试（单把密钥的上游超时）。对响应较慢的上游（长推理、高负载模型等），30 秒容易误判为失败，影响测试结果的可信度。

### 需求描述

1. 将模型测试的单次超时默认值从 30 秒调整为 300 秒（5 分钟）。
2. 覆盖范围：
   - 单模型测试（/channel/test）的整体超时；
   - 逐密钥测试（/channel/test_keys）中单把密钥的上游超时。
3. 逐密钥批量测试的整体预算需能容纳单把密钥 300 秒的超时，不被整体预算提前截断。

### 边界（不做）

- 不改变测试消息内容、测试并发数、结果展示等既有行为。
- 仅调整测试（channel_test）路径的超时；不影响转发请求的成员级响应超时等其他配置。

## REQ-007 日志上游协议展示统一为 openai_chat

### 背景

日志（请求追踪）中以「client_format → upstream_type」展示协议链。其中客户端格式统一使用下划线机器可读形式（openai_chat / openai_responses / anthropic），但上游为原生 OpenAI Chat Completions 渠道时，upstream_type 却显示为人类可读的「openai Chat Completions」，导致同一协议出现两种写法（如 `openai_chat → openai Chat Completions`），展示不一致。

### 需求描述

1. 日志中上游协议类型的展示统一为下划线机器可读形式：OpenAI 原生 Chat Completions 渠道由显示「openai Chat Completions」改为显示「openai_chat」。
2. 与客户端格式保持一致，当客户端与上游同为 Chat Completions 时，协议链统一展示为 `openai_chat → openai_chat`。

### 边界（不做）

- 仅统一日志中的展示名称；不改动其他协议类型（openai_responses、anthropic、自定义固定回复等）的展示。
- 不改变底层协议的实际处理逻辑与字段取值语义。

## REQ-009 模型测试按渠道协议透传

### 背景

当前模型测试固定以 OpenAI Chat Completion 协议构造请求，再经转换器转成渠道协议；日志中的 RelayMode 也硬编码为 converted。对非 OpenAI Chat 渠道（如 Anthropic、OpenAI Responses 等），测试路径与真实请求不一致。

### 需求描述

1. 模型测试直接以渠道设置的协议构造并发送测试请求（透传），不经过「OpenAI Chat → 渠道协议」的固定转换。
2. 测试结果与日志中的协议、relay mode 反映真实方式（透传或转换），与真实下游请求行为一致。

### 边界（不做）

- 渠道参数覆盖、模型限制、密钥选择、测试超时（300 秒）等既有测试语义保持生效；仅改变测试请求的协议构造方式（透传渠道原生协议）。

### 后续调整（2026-09-19）

「按渠道原生协议透传」在客户端协议 ≠ 渠道原生格式时（如客户端发 openai_chat、渠道是 anthropic）反而与真实转发路径分歧：透传/转换判定、完全透传 `raw.Path`、响应校验口径三处不一致，导致面板测试误判失败或回复提取为空。探针协议构造方式调整为以 `openai_chat` 作为代表客户端协议（`testProbeClientFormat`），路径决定与真实转发（客户端发 openai_chat）对齐。决定与因果见 [channel-test-probe-client-format](../.agents/notes/implemented/bug-fix/2026-09-19-channel-test-probe-client-format.md)。

## REQ-010 模型测试改为选择分组、按分组模型测试

### 背景

当前设置页「模型测试」以「渠道」为选择对象，对渠道下配置的模型逐个探测。而真实下游请求以「分组」组织（分组名即客户端模型名，成员为渠道+模型）。按渠道测试无法覆盖真实分组路由下的模型与协议。

### 需求描述

1. 设置页「模型测试」的选择对象从「渠道」改为「分组」。
2. 选中分组后，按真实下游请求的分组成员进行测试：对分组内每个成员（其指向的渠道与模型）发起测试。
3. 测试走真实分组路由逻辑（成员解析、成员选择、渠道协议、Relay 配置等），使测试结果与真实下游请求路径一致。

### 边界（不做）

- 引用成员（跨分组引用）按真实路由语义处理。
- 保持既有测试消息、超时（300 秒）、并发等需求不变。

## REQ-014 请求头模板新增 opencode 并更新 codex 版本号

### 背景

请求头模板（header_templates 设置项）供渠道表单「一键填充」自定义请求头，当前仅内置 codex 一个模板。需要补充 opencode 客户端的模板；opencode 的请求会话 id（x-opencode-session，会话级稳定 UUID）已由后端会话 id 注入能力提供。

### 需求描述

1. 请求头模板新增 opencode 模板，其静态请求头包含：
   - `x-opencode-client`: `desktop`
   - `User-Agent`: `opencode/1.18.31`
2. opencode 模板需覆盖「请求会话 id 注入」：即 `x-opencode-session`（会话级稳定 UUID），该值由后端的会话 id 注入能力生成，属于动态投值而非模板静态内容。
3. codex 模板的 User-Agent 版本号由 `0.147.0` 更新为 `0.154.0`（含 User-Agent 值内所有出现的版本号）。

### 边界（不做）

- opencode 模板中的会话 id 注入沿用现有 opencode 会话 id 机制（x-opencode-session），不新增另一套会话 id 逻辑。

### 后续变更

内置 OpenCode Free 固定渠道上线后，opencode 相关能力不再由自定义渠道承载：
- `header_templates` 出厂默认移除 opencode 模板；
- 渠道编辑器与 `ChannelUpdateRequest` 移除 `opencode_compat` 开关，自定义渠道创建时强制为 `false`；
- OpenCode 所需的 `x-opencode-client` / `User-Agent` / `x-opencode-session` 由内置渠道定义固定维护。

## REQ-015 请求脱敏前端管理页

### 背景

后端已完整实现请求脱敏与还原能力（`internal/relay/mask/` 引擎包 + `internal/server/handlers/mask.go` 管理 API + `handler.go` 链路集成），功能默认关闭。后端管理 API（`/api/v1/mask/{config,rules,test}`）已就绪，但前端尚无对应管理界面，管理员无法通过控制台配置规则、开启脱敏或预览效果。

## REQ-016 日志请求体/响应体格式化展示

### 背景

4. **内容标注**：展示区顶部标注内容格式（JSON / SSE / Text）与字节大小（如 2.3 KB），便于快速判断报文类型与体量。
5. **长内容折叠**：格式化后的内容超过一定高度时，默认折叠到固定高度并显示「展开/收起」按钮，展开后完整显示并支持滚动。
6. **统一组件**：以上能力封装为可复用组件，在追踪详情的请求体/响应体 Tab 与错误日志展开的请求体/错误详情中统一使用，保持视觉与交互一致。

### 边界（不做）

- 仅前端展示层格式化，不改变后端返回的原始内容与接口契约。
- 不做语法高亮着色（仅缩进与排版），避免引入额外语法高亮依赖。
- 不改变请求体/响应体的拉取时机与缓存逻辑（仍按 Tab 切换按需拉取）。

## BUG-003 3 年 / 永久趋势档位不显示用量数据

### 现象

仪表盘 Token 用量趋势图的「3 年」与「永久」档位不显示任何用量数据（图表显示"暂无用量数据"），而 24h / 7d / 30d / 1 年档位正常显示。实际上有用量调用记录，数据存在于 `usage_buckets` 表中。

### 根因

存在两处缺陷，共同导致 3y / forever 档位在数据全部较新时图表为空：

**缺陷一（后端，主因）：窗口点数不足，最近一个步长的数据被丢弃**

`internal/op/usage_bucket.go` 的 `UsageTrendPoints` 中，窗口定义为 `count = span / step`，起点 `start = now - span + 1h`。当前小时的桶映射到索引 `idx = int((now - start) / step) = int((span - 1h) / step)`。当 `span` 能被 `step` 整除时，`idx = count`，越界（有效索引 0 ~ count-1），最近一个 `step` 时长的数据被 `if idx >= count { continue }` 静默丢弃。

各档位实测：

| 档位 | step | count | idx(now) | 越界? | 被丢弃的最近数据 |
|------|------|-------|----------|-------|-----------------|
| 24h | 1h | 24 | 23 | 否 | 0h（无影响） |
| 7d | 6h | 28 | 27 | 否 | 5h（影响小） |
| 30d | 24h | 30 | 29 | 否 | 23h（影响小） |
| 1y | 7d | 52 | 52 | **是** | 最近 ~7 天 |
| 3y | 30d | 36 | 36 | **是** | 最近 ~30 天 |
| forever | 30d | 120 | 121 | **是** | 最近 ~30 天 |

1y 丢弃最近 7 天但更早的数据仍可显示；3y / forever 丢弃最近 30 天，若全部数据均在最近 30 天内（新部署常见），图表完全为空。

**缺陷二（前端，次因）：长序列截断保留最旧而非最新**

`web-next/src/lib/api.ts` 的 `normalizeTokenTrend` 末尾 `.slice(0, 60)` 将趋势点截断为前 60 个。forever 档位后端返回 120 个点（从最旧到最新排列），截断后保留的是最旧 60 个点，最新 60 个点（含实际数据）被丢弃。即使后端缺陷一修复，forever 仍会因前端截断丢失近期数据。

### 修复方向

1. **后端**：将各档位的 `count` 增加 1（或调整 `start` 计算），使最近一个步长的数据落入有效索引。例如 3y 的 count 从 36 改为 37，forever 从 120 改为 121。
2. **前端**：将 `.slice(0, 60)` 的上限提高到覆盖最大点数（如 130），或改为保留最新 N 个点而非最旧 N 个。

## BUG-004 渠道排序值行内编辑不保存

### 现象

### 涉及代码

`web-next/src/pages/Channels.tsx`：

- 第 114-140 行：`sortMut` mutation，调用 `api.updateChannel({ id, sort })`，乐观更新后 `onSettled` 清除草稿并 invalidate `["channels"]`。

后端 `internal/op/channel.go` 第 239-242 行：`req.Sort != nil` 时将 `sort` 加入 `selectFields` 并赋值，GORM `Select(selectFields).Updates(&updates)` 写入。

### 修复方向

- 确认 GORM `Select + Updates` 对零值的写入行为，必要时改用 `map[string]any` 构造更新值避免零值跳过。
- 在 `normalizeChannels` 中对 `sort` 做显式归一化（`typeof channel.sort === "number" ? channel.sort : 0`），与 `rate_limit_rpm` / `max_concurrent` 一致。
- 考虑为排序输入增加 `onKeyDown` Enter 提交之外的即时提交机制（如 `onChange` 防抖提交），避免依赖 `onBlur`。

## BUG-006 编辑渠道点保存无反应且改动不生效

### 现象

渠道编辑器内修改内容后点击「保存」，无任何反馈（不出现「已保存」，也无报错），关闭后重新打开仍是旧值；同样的编辑操作在分组页正常。

### 根因

两层问题叠加，均产生「静默不生效」：

1. **前端对未变更字段做拦截**：编辑器保存按钮 `disabled={!isValid}`，而 `isValid` 对名称/地址做实时校验（`NAME_RULE`/`URL_RULE`）。存量渠道的名称可能来自导入或旧版本（如含中文括号、全角冒号等 `NAME_RULE` 不允许的字符；导入接口本身不做该校验，后端也仅要求非空+唯一），编辑这类渠道时按钮永久禁用，点击无反应且无任何错误提示。
2. **后端空更新静默成功**：`op.ChannelUpdate` 依赖指针字段判 nil 决定更新列；若请求未携带任何可更新字段（异常客户端/回归），事务内不执行任何写操作却返回 200，前端提示「已保存」但读回旧值。

`web-next/src/pages/channels/channel-editor.tsx`：编辑态只校验「用户改过的」字段——`nameChanged`/`urlChanged` 以打开编辑器时的渠道值为基线做比对，未变更的字段不再参与校验；新建或修改后的值仍走完整校验。

`internal/op/channel.go`：`ChannelUpdate` 在 `selectFields`、`sortUpdateVal` 与 `req.Models` 均为空时返回「请求未包含任何需要更新的字段」错误，不再静默成功。

3. 界面文案统一为「优先级」，不再出现「排序值」。

### 边界（不做）

- 不新增独立保存接口；随渠道编辑器既有保存请求提交。
- 不把后端 JSON 字段 `sort` 改名为 `priority`。

## REQ-021 渠道/分组保存后列表即时更新

### 背景

保存渠道/分组的界面更新此前完全依赖「保存成功 → invalidate → refetch 列表」的二次往返。线上访问链路为 移动端 → 本地代理 → Cloudflare → kdns 隧道 → 源站，单次 API 往返就有可感知延迟，两次叠加后保存后列表明显滞后；若 refetch 偶发拿到旧响应，界面会长时间停留在旧值。

### 需求描述

1. 渠道编辑器、分组编辑器保存成功后，把保存接口返回的最新实体（后端已刷新并归一化）直接写入 React Query 列表缓存（`setQueryData` 替换/追加），界面立即反映改动；invalidate 的 refetch 降级为后台一致性兜底。
2. 渠道/分组的删除先从本地缓存移除该条目再后台校对；渠道复制的新实体即时入列。
3. 分组「自定义」排序的上移/下移改为乐观更新：本地立即按后端 GroupList 同款规则（display_order≠0 者在前按值升序，其余按名称）重排，失败回滚。
4. `api.ts` 抽出 `normalizeChannelOne` / `normalizeGroupOne` 单实体归一化，create/update/active 接口返回值与列表数据同形，保证写回缓存不缺字段。

### 边界（不做）

- 不改动后端任何接口与缓存逻辑；保存响应本就返回刷新后的完整实体。
- 不引入 WebSocket/SSE 推送列表变更；跨标签页一致性仍由 refetch 兜底。

## REQ-022 移植前端缓存策略

### 背景

针对「保存成功但前端滞后」依赖三件套兜底：列表 30s 轮询自愈、行内编辑防抖+串行队列、4xx 不重试。NovaVeil 已有「保存响应直写缓存」（REQ-021），再把这三件搬过来补齐。

### 需求描述

1. 列表兜底轮询：渠道/自定义模型/分组（含其渠道观察者）/密钥/设置列表查询统一 `refetchInterval: 30_000`，invalidate refetch 延迟或丢失时最迟 30s 自动对齐后端。
2. 智能重试：4xx 确定性失败不重试（避免把失败放大成请求风暴），其余保留指数退避重试（`main.tsx` QueryClient 默认）。
3. 优先级行内编辑抽为共享组件 `components/ui/priority-input.tsx`：加减按钮防抖保存（500ms 合并连续点击）、失焦/回车立即提交、同渠道保存经串行队列防乱序、乐观更新失败回滚快照、服务端值追平前不覆盖用户草稿。渠道页与自定义模型页（表格/卡片两种视图）统一复用。

### 边界（不做）

- 不迁移模块级单例 queryClient / queryOptions 工厂架构（现有结构已够用）。
- 不引入日志页 SSE；日志实时性按现有实现保持。
- 优先级仍允许负数与重复值，不引入 ≥0 截断。

## REQ-023 请求脱敏规则扩展 MAC 与 USCC

### 背景

请求脱敏（REQ-015）落地了 10 类内置规则（PRIVATE_KEY / API_KEY / CONNSTR / PHONE / EMAIL / IDCARD / CARD / SECRET / JWT / TOKEN）。实际使用中发现两类高价值敏感实体尚未覆盖：网卡 MAC 地址与统一社会信用代码（USCC），需要作为内置规则增量扩充。

### 需求描述

1. 在脱敏规则引擎 `internal/relay/mask/rules.go` 新增两类内置规则：
   - `MAC`：6 组两位十六进制（分隔符为冒号 / 连字符 / 点），无额外校验，仅依赖「形状 + 两侧非字母数字」边界约束，排除更长十六进制串或哈希串的中间片段。
   - `USCC`：18 位统一社会信用代码，字符集为 31 进制（禁 I/O/S/V/Z），末位为前 17 位按 MOD 31 加权算法计算的校验位（GB 32100-2015），校验不通过即拒绝替换。
2. 两类规则同步登记到 `BuiltinRules`（规则定义）与 `BuiltinRuleMeta`（元信息），标签一致，前端管理台自动渲染开关，无需前端改动。
3. 复用现有「默认全关」硬约束：`MAC` / `USCC` 出厂默认关闭，管理员按需开启；命中后占位符后缀继续用 `crypto/rand` 安全随机。
4. 命中明细（`{label, original, placeholder}`）沿用现有 `MaskResult.Matches`，供管理台脱敏测试预览。

### 边界（不做）

- 不做 MAC 厂商信息解析（OUI 反查）、不做信用代码主体登记信息解析。
- 不改变现有 10 类规则的标签、开关键、执行顺序与占位符格式，仅作规则集增量扩充。
- 不新增任何配置项类型，复用现有 `BuiltinRuleSwitch` 标签开关机制。

## REQ-024 模型评估四视图与持久化排序 / 评估队列 / 历史裁剪

### 背景

原先「模型评估」仅能单条发起并即时展示结果。用户需要一个围绕「渠道 + 模型」的评估工作区：跨渠道维护优先级排序，并固化到 `auto` 分组；评估以队列方式顺序执行、可管理；评估历史可回看、复用并按规则裁剪。

### 需求描述

1. **四视图页面结构**：模型评估页按「当前评估 / 评估排序 / 评估队列 / 评估历史」顺序提供四个视图，职责单一、可随时切换互不干扰。
2. **当前评估**：勾选「渠道 + 模型」发起评估；发起后任务加入评估队列末尾排队执行，不再中断既有评估。
3. **评估排序（持久化）**：跨渠道模型有序列表，`position` 越小越靠前。请求成功即可入列，不按格式合规自动分区：`ok` 与 `violation` 都按 `position` 排列；`error` 不写入排序，也不覆盖该「渠道 + 模型」已有的成功快照。已在排序中的成功条目再次评估成功时保留原 `position`。持久化到 `model_eval_ranks`，同一「渠道 + 模型」只有一行快照。支持上移 / 下移 / 移除（移除不删历史）、从评估历史加入排序，并在列表下方/右侧内嵌 SVG 预览（受限 sandbox + CSP）。
4. **更新 auto 分组（容错）**：接口仍是 `POST /api/v1/model-eval/rank/apply-pro`，写入的分组名称是 `auto`，不是 `pro`。以当前排序里的 `ok` / `violation` 整体原子替换 `auto` 成员。按 `position` 升序写入，`priority` 从 1 递增，路由按数值小者优先。这和渠道列表的 `sort`（数值越大越靠前，且不参与选路）不是同一套语义。渠道停用但模型仍在的记录保留入组并保持原排名；模型删除/改名的失效记录在同事务内清理，不因单个记录不可用而整体中止。全部失效时仅清理并返回「没有可用于分组的评估结果」，不产生空分组。事务失败回滚，不允许出现「删了旧成员未写新成员」的半空分组。响应附 `kept_disabled`（保留的停用渠道模型）与 `cleaned_stale`（清理的失效记录）两类处理说明。
5. **评估队列（持久化 + 常驻调度）**：落地 `model_eval_queue` 表；常驻调度器（worker 池，最多 4 个并发）按 `position` 顺序出队执行。10 分钟是任务开始执行之后的超时，不是排队等待上限。支持单个模型向上调整一格、停止单个模型、清空整个队列；禁止停止/调整「正在执行」的评估，清空不中断执行中的评估。队列状态经 SSE（`/queue/stream`）推送。
6. **评估历史清理**：每个「渠道 + 模型」的成功记录仅保留最近三次（自动裁剪，幂等），失败记录可一键「清空失败记录」（二次确认、不可逆）；裁剪不作用于 error 记录，已载入排序的条目不因裁剪失效。
7. **接口统一走 `/api/v1/model-eval/*`**，新增 `model_eval_ranks`、`model_eval_queue` 两张表（AutoMigrate），既有 `model_evals` 表结构不动。

早期表述曾写成：`violation` 默认排在 `ok` 之后、`error` 留在列表底部、无条件只保留最新一次评估、`priority` 递减且首项数字最高、排队最多等 10 分钟、目标分组叫 `pro`。现行实现不是这些。管理台排序列表会显示已经入列的 `violation`；「加入排序」按钮目前只对 `ok` 可点，比 `POST /api/v1/model-eval/rank/from-history` 更窄（该接口接受 `ok` 和 `violation`）。这次只校正记录，不改这个按钮。

「更新 auto 分组」以容错分类替代原先「任一失效即整体中止」的语义（渠道停用保留、失效清理、事务内按库复核闭合悬空分组成员竞态），决定与因果见 [model-eval-group-replace-tolerance](../.agents/notes/implemented/bug-fix/2026-09-19-model-eval-group-replace-tolerance.md)。

### 边界（不做）

- 不改变评估题目与包裹格式判定（沿用既有固定题目与 `<<<RESULT>>>` / `<<<END>>>` 判定）。
- 排序与队列的并发执行沿用既有受控并发（上限 4），不引入新的并发模型。
- 前端 SVG 预览仅作为排序结果的展示，不负责评估执行。
- 新增常驻调度器放独立 `internal/eval` 包以规避 `op ↔ relay` 循环依赖。

## REQ-025 免费渠道与自定义渠道选路一视同仁

### 背景

早期实现中，内置免费渠道（`IsFree=true`）在故障转移选路中被整体前移到付费渠道之前，即 `freePriorityOrderedItems` 会把免费渠道排到候选列表最前面，使其优先于优先级更高的付费渠道被选中。这导致：

1. 管理员把免费渠道加入混合分组（本意是作为故障兜底）时，用户的第一个请求就会路由到第三方免费渠道，而非管理员配置的高优先级付费渠道。
2. 请求成功后会因 `MemberAffinitySeconds` 粘合在免费渠道上，后续请求持续外发到第三方。
3. 代码注释写"故障转移中优先"但实际是主路径首选，注释与行为不一致，易误导管理员。

### 需求描述

1. 移除 `freePriorityOrderedItems` 及 `itemIsFreeChannel` 函数，选路不再按免费/付费分类做任何重排。
2. 故障转移严格按分组成员的优先级顺序（Priority 升序）依次选择，免费渠道与自定义渠道一视同仁。
3. `PreferPassthrough` 协议重排保持不变：同协议成员整体前移，但分类不参与重排。
4. `IsFree` 字段保留用于前端展示（免费徽标、筛选）和内置渠道不变量维护，不再影响路由顺序。

### 边界（不做）

- 不移除 `IsFree` 字段本身，它仍用于前端渠道列表的免费筛选和徽标展示。
- 不改变 `EnsureBuiltinFreeChannels` 的强制不变量逻辑（内置渠道恒为 `IsFree=true`，自定义渠道恒为 `IsFree=false`）。
- 不改变 `PreferPassthrough` 协议重排行为。

## REQ-026 内置免费渠道默认关闭 AutoSync 与代理

### 背景

早期实现中，9 个内置免费渠道全部默认 `AutoSync: true`，服务启动时同步任务 `runOnStart: true` 即自动执行，对所有 AutoSync 渠道发 `GET /v1/models`。这导致每次启动 NovaVeil 都会向 9 个第三方域名发起 outbound 请求，无需管理员任何操作，暴露服务器公网 IP 与实例存在性。

此外，内置免费渠道的 `Proxy` 字段默认为 `false`（Go 零值），即使管理员在设置页配置了系统代理 `proxy_url`，内置免费渠道的模型同步与请求转发均走直连，不经过代理。

### 需求描述

1. 内置免费渠道出厂 `AutoSync` 默认为 `false`：启动时不再自动向第三方域名拉取模型列表。管理员按需在渠道编辑器手动开启 AutoSync 后，同步任务才会对该渠道拉取 `/v1/models`。
2. 内置免费渠道出厂 `Proxy` 默认为 `false`（直连）：如需通过代理同步模型或转发请求，管理员需在渠道编辑器手动开启代理开关（系统代理或渠道专属代理）。
3. 渠道定义注释明确标注 AutoSync 与 Proxy 的默认值与管理员手动开启的方式。
4. 已存在的内置渠道不受影响：`EnsureBuiltinFreeChannels` 只补建缺失的渠道，不覆盖管理员对已有渠道的个性化修改。

### 边界（不做）

- 不强制重置已存在内置渠道的 AutoSync/Proxy 值：尊重管理员可能已做的修改。
- 不移除 AutoSync 功能本身：管理员仍可手动开启。
- 不改变同步任务的 `runOnStart` 行为：仅通过渠道级 AutoSync=false 控制是否对该渠道同步。

## REQ-027 内置官方渠道（用户自行配置 Key 与模型）

### 背景

内置免费渠道覆盖了无需认证的第三方端点，但管理员常用的官方付费 API 提供商（OpenRouter、OpenCode 付费端、NVIDIA NIM 等）每次都需要手动创建渠道、填写 BaseURL、配置 Key 和同步模型。将常见官方提供商预置为内置渠道，管理员只需填入自己的 API Key 即可使用，减少重复配置工作。

### 需求描述

1. 新增 `BuiltinOfficialChannels` 内置官方渠道清单（`internal/builtin/official.go`），当前收录：
   - **OpenRouter**：`https://openrouter.ai/api`，聚合数百个模型的 OpenAI Compatible 网关。
   - **OpenCode**：`https://opencode.ai/zen/go`，OpenCode 官方付费端点。
   - **NVIDIA NIM**：`https://integrate.api.nvidia.com`，NVIDIA 托管的开源模型推理端点。
2. 官方渠道与免费渠道的出厂默认值不同：
   - `IsFree = false`（非免费，需要用户自己的 API Key）；
   - `Enabled = false`（出厂禁用，用户填入 Key 并启用后才参与路由）；
   - `AutoSync = false`（出厂不自动同步，用户填入 Key 后手动开启同步拉取模型列表）；
   - `Key` 为空、`Models` 为空（全部由用户通过渠道编辑器自行配置）。
3. `EnsureBuiltinChannels` 在启动时自动补建缺失的内置渠道（`cmd/start.go`），包括免费渠道和官方渠道，已存在的同名渠道不覆盖，尊重管理员已做的修改。
4. 官方渠道 `Builtin = true`，与免费渠道一样受删除保护（不可删除，如不需要可停用）。
5. 前端分类筛选统一为三类：**免费**（is_free=true）、**内置**（builtin=true, is_free=false，即官方渠道）、**自定义**（builtin=false，用户创建的渠道）。

### 边界（不做）

- 不预置 API Key：官方渠道出厂 Key 为空，由管理员通过渠道编辑器自行填入。
- 不预置模型列表：官方渠道出厂 Models 为空，由管理员填入 Key 后手动同步或添加。
- 不自动启用：官方渠道出厂 Enabled=false，管理员配置完成后需手动启用。
- 不强制重置已存在官方渠道的配置：尊重管理员可能已做的修改。
