## 1. 文档定位与目标

[PLAN.md](PLAN.md)、[DESIGN.md](DESIGN.md) 和两份 `AUDIT` 文档主要记录静态原型阶段。本文承接原型方向，但针对当前生产前端制定后续工作，不将原型能力、模拟数据或原型审计结论直接视为生产实现。

后续美化优先解决三个问题：

1. **统一**：同类工具栏、搜索、筛选、空态、表单和反馈采用同一套组件与状态语言。
2. **可用**：窄屏、键盘操作、深浅主题和异常状态下，用户仍能识别信息并完成操作。
3. **克制**：保留冷白磨砂与蓝色强调，优先改善信息层级，不用装饰图表和过多动画掩盖真实状态。

本轮不扩大到路由策略、计费、认证机制或后端接口重构。现有业务行为修复单独记录在 [FEATURES.md](../FEATURES.md)，不能因样式调整被覆盖。

### 3.4 业务交互已有实现与回归边界（2026-09-16 源码核对）

以下不再作为“从零新增”任务，但仍需运行验收；不可在美化或性能改造时退回旧行为。

- **列表编辑与缓存**：渠道编辑器、`CustomModels.tsx`、`Groups.tsx` 保存前取消对应在途查询，成功后把服务端返回实体写入列表缓存，再由页面回调触发后台失效刷新。渠道启停、分组自定义排序另有乐观更新与失败回滚。下一步验证慢请求、失败、连续修改和跨页返回，不将“保存回填已实现”等同于“全站 Query 策略已统一”。
- **渠道/自定义模型优先级**：共享 `components/ui/priority-input.tsx`，有 500ms 加减防抖、回车/失焦提交、串行保存和缓存回滚；数值越大越靠前，同值按名称排序。分组列表的自定义顺序与成员 `priority` 是不同语义，成员按较小 priority 优先，成员名次输入已存在。下一步保留这些语义并核验失败后草稿、并发编辑及重载顺序。
- **模型评估与分组联动**：`ModelEval.tsx` 与 `components/model-eval/` 已接入服务端队列、历史复用、名次调整、移除及应用到自动分组；不是待新增页面。仍有待核对的不一致：`EvalRanking.tsx` 的 `rankable` 接受 `ok` 或 `violation`，而界面文案和历史复用按钮只允许格式合规的 `ok`。需结合实际接口返回确认旧数据兼容与排序/分组资格，不能仅凭文案宣称已一致。
- **渠道模型批量操作**：`pages/channels/channel-editor.tsx` 已有搜索子集勾选、删除所选、测试所选/全部及四 worker 并发测试；关闭、切换渠道或卸载时有停止后续派发的标记。该标记不等于取消已发送的计费请求。下一步验证跨轮次晚到响应、关闭后重开、部分失败、筛选后选中范围和删除草稿的保存边界。
- **路由性能**：分类骨架、路由滚动复位和导航 chunk 预加载仍待实施；分组已有部分 `useMemo`，列表缓存回填也已落地，后续应补缺而非重复实现。详细状态见 [路由性能规划](ROUTE_TRANSITION_PERFORMANCE_PLAN.md)。

上述相关测试源码包括 `Channels.test.tsx`、`CustomModels.test.tsx`、`Groups.test.tsx`、`components/ui/priority-input.test.tsx` 与 `lib/model-eval.test.ts`，仅作为后续检查入口，本次未运行，不能据此勾选验收。

## 4. 后续统一规范

### 4.1 视觉与信息层级

- 正文、次级文字和提示文字分别使用现有 `ink` 系列令牌；操作强调使用 `primary` / `primary-text`，危险操作使用 `destructive`。
- 品牌图形允许保留自身颜色。图表确需独立系列颜色时集中定义，不在多个页面重复散落色值，并同步检查深色主题与图例。
- 默认沿用 `rounded-card`、`rounded-control` 和已有阴影层级。例外尺寸应服务于内容，而非每页自行定义一套风格。
- 一个操作区优先呈现一个主要动作；删除、重置、清空等动作与常规操作拉开层级，保留确认和禁用逻辑。
- 数字采用等宽数字排版；名称过长可截断，但需保留查看完整内容的途径，不能隐藏关键状态或操作。

### 4.2 状态与反馈

- 加载中、真实空数据、筛选无结果、请求失败分别呈现，不能统一显示“暂无数据”。
- 首次空态说明如何开始；筛选空态提供清除筛选入口；失败态提供明确错误和重试入口。
- 保存期间提供忙碌反馈并避免重复提交；失败后保留输入，不把服务端错误包装成成功提示。
- 状态至少配合文字或图标表达，不只依赖红绿颜色、闪烁或动画。
- Toast 适合结果通知；阻止继续操作的错误应同时留在对应表单或页面区域。

### 4.3 响应式与可访问性

- 页面内容优先重排，数据表、代码块等确需横向滚动的区域单独承担滚动，不让整个页面被撑宽。
- 搜索、分段筛选、排序和主操作在小屏下允许换行；不能简单缩小文字和点击区域来保住单行布局。
- 保持清晰的主标题层级，统一检查导航、对话框、表单控件和纯图标按钮的可访问名称。
- 键盘必须能进入、操作、退出弹层，并在关闭后回到合理位置；桌面折叠状态不能破坏移动抽屉的可用性。
- 移动端常用操作尽量提供 44×44 CSS px 点击区域。WCAG 2.2 AA 的最小目标尺寸检查与移动端舒适尺寸分开记录，不混为同一标准。
- 不假设公共组件自带样式就意味着通过无障碍验收；焦点、对比度和读屏表现以实际交互验证为准。

## 5. 分阶段任务清单

下列复选框表示**后续工作及验收尚未完成**，不是对已有源码的否定。优先级是美化实施顺序，不是安全漏洞等级。

### P1：一致性与基础可用性收口

- [ ] **补齐品牌入口。** 将 `App.tsx` 的 `RollbackNotice`、`components/auth/ForceChangePassword.tsx` 中的手写渐变字母标识纳入 `BrandMark` 统一范围；保留页面标题和强制改密逻辑。验收：登录、侧栏、改密、回退页使用同一品牌图形，没有重复或缺失的主标题。
- [ ] **补齐脱敏页公共空态。** `Mask.tsx` 的“暂无内置规则”“还没有自定义拦截词”等仍为独立结构。区分规则列表空态与试运行结果态，按场景复用 `EmptyState`，不机械替换所有提示区域。验收：首次配置入口清楚，加载或错误不被误报为空数据。
- [ ] **补齐移动抽屉焦点管理。** `AppShell` 当前由普通容器和遮罩构成，已处理 Escape 与滚动锁定，但未见完整的模态焦点管理。后续补齐打开后的焦点进入、Tab 约束、关闭后的焦点恢复、背景不可交互及显式关闭入口。验收：仅用键盘可完整操作，折叠侧栏后切到小屏仍可辨认导航。
- [ ] **恢复可发现的命令面板入口。** `TopbarProps` 保留 `onOpenCommand`，但当前 `Topbar` 没有使用它，面板主要依赖快捷键打开。补充可点击入口并标明快捷键，避免在窄屏挤占核心操作。验收：鼠标、触控和键盘都能进入面板。
- [ ] **检查工具栏与时间筛选重排。** `SearchField` 默认 `w-56`，`SegmentedControl` 默认不换行，总览时间选择有六个选项。逐页检查父容器与控件组合，按需提供满宽、折行或局部滚动布局。验收：390px 和 320px 下无意外页面横向滚动，搜索和主操作均可达。
- [ ] **统一语义与焦点检查。** 检查 Topbar 标题与页面内容标题层级、搜索框名称、图标按钮、分段控件和视图切换的焦点可见性及选中状态。验收：不依赖 placeholder 或颜色理解控件用途，Tab 顺序与视觉顺序一致。

本阶段完成标准：共用布局和高频控件完成收口，关键操作不再因窄屏或键盘使用而不可达，并有对应验收记录。

### P2：页面信息层级与真实数据表达

- [ ] **总览优化。** 先整理 KPI、趋势、模型 Top 和最近错误的主次关系，并明确模型 Top 的加载/失败状态；当前它仅按 `top.length` 判断空态，而统计请求在页面顶部单独提示错误。图例当前存在独立色值，后续与实际图表一起统一检查。
- [ ] **管理页密度统一。** 渠道、分组、自定义模型、密钥页统一表头、状态标签、操作区、长文本和批量操作的视觉规则；保留已有排序、编辑校验与数据刷新行为。
- [ ] **日志详情可读性。** 用摘要、关键字段、完整正文分层展示；长 JSON、代码块和追踪信息可独立滚动。大列表继续保留虚拟化，不因卡片化而退回一次性全量渲染。
- [ ] **对话布局优化。** 检查长消息、代码块、无可用模型、发送中、流式失败和停止后的布局；优先保证输入区可达，不改变中继请求行为。
- [ ] **设置与编辑器统一。** 按功能区分组设置项，统一说明文案、校验提示、按钮位置和对话框滚动边界；长标题不能覆盖关闭按钮。
- [ ] **材质与动效收敛。** 现有透明度降级主要覆盖 `glass-*` 类，而部分控件直接使用 `backdrop-blur-sm`。检查这些区域是否也需要降级，以及常驻模糊层是否可以减少；不得以装饰收益为理由增加明显滚动负担。

本阶段完成标准：核心页面的正常、加载、空、失败与恢复状态都有一致表达；长内容和大数据量不破坏布局与操作反馈。

### P3：可选增强，独立评估后再实施

- [ ] **模型分布图。** 若新增甜甜圈，明确“Top 模型 + 其他”的统计口径，使用当前时间范围的真实数据；不能把现有相对最高模型的进度条直接当成占比数据。
- [ ] **渠道健康摘要。** 先明确运行状态、熔断、冷却与延迟等数据含义，再设计摘要卡；没有真实健康度指标时不绘制假百分比条。
- [ ] **迷你趋势与活动时间轴。** 必须有对应时间序列或事件来源、时间范围、刷新方式与空态定义；没有数据时保留当前真实摘要，不复制原型模拟曲线。
- [ ] **公开落地页。** 作为独立产品需求评估公开内容、路由和访问边界，不为了美化改动现有登录与强制改密入口。
- [ ] **导航增强。** 先评估命令面板是否已满足快速定位需求，再考虑侧栏搜索、置顶或排序；不重复堆叠入口。

本阶段不作为 P1/P2 交付的前置条件，也不默认引入新图表库、动画库或外部字体资源。

## 7. 实施、验证与交付方式

### 7.1 实施顺序

1. 先公共组件与布局，再高频列表页，最后复杂详情和可选可视化。
2. 每批变更围绕一个可验收主题，不把全站样式、业务修复和新增后端能力捆绑交付。
3. 复用已有 React、Tailwind、Radix 与图标体系；公共组件不能为单个页面的装饰需求承担不必要的复杂接口。
4. 调整交互时补充对应测试源码，保留现有业务回归用例；测试文件存在不等于已运行通过。

### 7.2 验证边界

- 本地仅阅读与编辑，不安装依赖、不构建、不启动服务、不运行测试。
- 由用户、远端环境或 CI 执行验证。已有 `package.json` 提供 `lint`、`typecheck`、`test`、`build` 与 `size` 脚本；按实际变更选择并记录结果。
- 现有 `web-next/e2e/smoke.spec.ts` 与 `web-next/e2e/a11y.spec.ts` 可作为端到端和无障碍覆盖入口，新增交互场景应补入相应验收流程。
- 组件测试重点覆盖搜索值与属性透传、选项切换、选中状态、表单校验和关键事件；浏览器验收重点覆盖排版、焦点、响应式、对比度和滚动。
- 视觉验收针对实际生产构建，不以 `prototype/` 截图代替，也不以静态检查或测试脚本存在代替真实运行结果。

### 7.3 每阶段完成定义

- [ ] 对应代码已落地，文档中的差异和任务状态同步更新。
- [ ] 所需静态检查、组件测试与构建已由远端或 CI 执行，保存真实结果；失败项不标记完成。
- [ ] 本阶段涉及页面完成深浅主题、桌面和移动端视觉及交互验收。
- [ ] 关键业务路径回归通过，没有破坏登录、改密、保存、筛选、排序、复制、日志查看或对话发送。
- [ ] 已注明构建/版本标识、验证环境与未解决问题，可区分“代码存在”“已验收”“已部署”。

验收记录建议每次追加一条，至少包含：日期、变更范围、版本/提交、环境、视口与主题、操作步骤、实际结果、结论及剩余问题。未经验证的项目保持未勾选。
