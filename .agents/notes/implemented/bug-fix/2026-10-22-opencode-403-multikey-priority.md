# Agent Note: 多 Key OpenCode 渠道 403 不冷却 Key

Status: implemented

## 问题

OpenCode 免费档的 403 表示代理账号对应出口 IP 被封，只应冷却账号并换号重试。上一版已经把 403 接入账号换号分支，但多 Key 渠道先命中了认证拒绝的 Key 轮换分支：请求会先冷却本轮 Key 再 `continue`，无法进入账号换号逻辑。

这会同时惩罚 Key 与账号。坏出口存在时，可用尝试次数退化为渠道的 Key 数量，而不是每成员固定的换号预算；Key 耗尽后请求还会提前进入成员失败路径，与“403 只换账号”的既定口径冲突。内置 OpenCode 渠道只有单 Key `public`，正常运行不触发；管理员手工配置多 Key 后才会复现。

## 决定

多 Key 渠道是否会因认证拒绝轮换 Key，由本轮错误与代理使用状态共同决定：

- 401 仍按原语义冷却当前 Key、轮换到同一成员的下把 Key。
- 429 仍按原语义冷却当前 Key、轮换到同一成员的下把 Key。
- 403 且本轮使用了代理账号（`proxyAccount != ""`）时，不冷却 Key，继续进入既有代理账号换号分支。
- 403 但本轮没有使用代理账号时，保留原有 Key 轮换语义。

实现只在原来的多 Key 分支上增加 403 与 `proxyAccount` 的排除条件，不移动分支顺序；取消、管理端终止与轮次取消的判定路径保持原状，换号预算、`opencodeAccountPinned` 固定复用、超过上限后回落成员失败路径也保持不变。

多 Key 的普通选 Key 游标仍按每轮轮询推进；本次约束只禁止因 403 冷却 Key，不额外固定 403 换号期间使用的 Key。

## 备选方案

- **把代理账号换号分支整体上移到多 Key 分支之前** — 所有错误的处理顺序会更直观，但会改变 401、429 以及其他 403 场景的优先级，并需要重新验证取消、终止与换号预算的先后关系；只调整多 Key 分支条件能保持其余契约不变。
- **把 403 从 `isAuthRejectionError` 中全局移除** — 条件最集中，但会同时改变非 OpenCode、无代理账号与其他多 Key 渠道对 403 的既有处理，影响范围超出本缺陷。
- **403 换号期间固定复用同一把 Key** — 可减少 Key 轮换，但需要新增请求级 Key 固定状态，并改变多 Key 渠道既有的逐轮轮询语义；任务只要求 403 不冷却 Key，没有证据表明同一坏出口与具体 Key 绑定。

## 后果

- **收益**：多 Key OpenCode 渠道的 403 只消耗账号池，不再污染 Key 健康度；每个成员仍可使用完整的三次换号预算，坏出口不会把可用尝试压缩到 Key 数量。
- **代价与已知上限**：403 换号期间 Key 仍可能随正常轮询变化，排障时需同时看 Key 标签与代理账号；若未来上游开始把封锁与具体 Key 绑定，需要重新评估 Key 固定策略。
