# Agent Note: 上下文探测窗口草稿与分组窗口展示

Status: implemented

## 问题

模型评估页的窗口输入框在保存请求期间仍可编辑，但成功回调无条件删除草稿。用户在等待保存时继续输入的新值会被旧请求的回调清掉，界面跳回旧的人工窗口。同一处把空输入解释为 `context_window=0`，而页面已有独立「清除」按钮；清空输入框后保存会意外清除人工窗口。分组页把 `131072` 显示成 `131K`，tooltip 也不带精确 token 数，管理员无法从界面确认实际窗口。

## 决定

- 保存窗口时快照提交草稿；请求成功回调只在当前草稿仍等于该快照时删除，保存期间的新输入原样保留。
- 空输入永不提交，保存按钮按空输入禁用并提示使用清除按钮；`context_window=0` 只由「清除」按钮发送。
- 新增文案集中在 `web-next/src/locales/zh-CN.ts` 的 `contextProbe` 段。
- 上下文窗口显示保留最多三位小数（`131072 → 131.072K`），tooltip 同时给出精确值 `131,072 token`。

## 备选方案

- **保存期间禁用输入框**：能避免竞态，但会让连续调整多个模型的流程频繁卡顿；否掉。
- **继续把空输入当 0 提交**：实现最少，但用户误清空即可抹掉人工窗口，与独立清除按钮语义冲突；否掉。
- **用 `Intl.NumberFormat` 的 compact 记法**：代码更通用，但默认仍会把 `131072` 舍入成 `131K`，达不到显示精确值的目标；否掉。

## 后果

- **收益**：保存与继续编辑可以并发；人工窗口不会被空输入误清除；成员窗口展示能精确到 token，同时保留紧凑 K/M 后缀。
- **代价与已知上限**：草稿在请求成功时若已被改动会继续保留，用户需要再保存一次；三位小数对极大窗口仍可能省略个位，但 tooltip 始终给出完整值。

## 验证

- `cd web-next && pnpm test -- ContextProbe Groups`
- 人工检查：保存请求未返回时把输入从 `128000` 改为 `256000`，响应后输入仍为 `256000`；清空输入后保存按钮禁用；点击清除仍提交 `context_window: 0`。
