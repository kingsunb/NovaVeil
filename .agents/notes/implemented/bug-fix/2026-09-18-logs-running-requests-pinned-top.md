# Agent Note: 日志实时列表运行中请求置顶

Status: implemented

## 问题

日志页实时请求列表（`web-next/src/pages/Logs.tsx`）此前完全按请求 ID 倒序展示：最新到达的请求在最上面，往下依次更旧。列表里同时存在「正在请求/响应中」与「成功/失败/已取消」两类记录时，运行中的请求如果 ID 较小，会被压到更早的请求之下，管理员需要向下翻找才能盯住仍在进行的请求。

后端的 SSE 快照按请求 ID 倒序发出，这个顺序在状态插入层是刻意保持的（`onMessage` 里的插入逻辑），问题只出在展示层没有把「运行中」提升为第一排序键。

## 决定

在 `LogsPage` 中新增展示层排序 `visibleLive`，保持状态源 `live` 仍按后端 ID 倒序维护不变：

- 第一排序键：请求是否仍在运行，`status === "running" || status === "committed"` 的请求置顶；
- 第二排序键：同一分组内部仍按请求 ID 倒序（最新在顶），沿用后端快照顺序。

排序只作用于传给 `LiveTable` 的 `rows`，`tracing`（追踪详情按 ID 从 `live` 查找）与顶部计数统计继续基于 `live`，不感知展示顺序。`live` 的合并/更新逻辑（ID 倒序插入、200 条截断）原样保留。

## 备选方案

- **直接在 `live` 状态里维护「运行中在前」** — 最强论据是排序计算不重复执行、状态与展示一致；否掉因为 `live` 同时被 `onMessage` 的 ID 倒序插入逻辑和 `tracing`/统计消费，改成双排序键会污染状态语义，且新增终态请求时还要按分组决定插入位置，复杂度向状态层扩散；展示层过滤排序改动最小。
- **只把 `running` 置顶，`committed`（响应中）不置顶** — 最强论据是「正在请求」才是用户最关心的阶段，`committed` 已进入响应阶段；否掉因为顶部计数「运行」口径同时包含 `running` 与 `committed`，且 `committed` 仍在耗时、未定稿，列表若只置顶 `running` 会出现「运行中」计数与置顶行不一致，语义更绕。

## 后果

- **收益**：日志页打开后，所有仍在进行的请求固定出现在列表顶部，按最新在顶排列；已终态请求顺延到下方，不再遮挡运行中请求。展示层排序不影响 SSE 合并、追踪详情、统计计数的既有行为。
- **代价与已知上限**：请求从 `running/committed` 变为终态时会从顶部组移到下方组，正在盯着的行可能发生一次位置跳动；这是「运行中置顶」排序的自然代价，列表每行有稳定 `aria-label` 供定位。未来若需要「置顶但终态行原地淡出/保持位置」，需要引入额外的锚定策略，当前不做。

## 验证

`web-next/src/pages/Logs.test.tsx` 的实时列表顺序用例已改为断言「快照 5→1 时先置顶 #5、#2（running），其余 #4、#3、#1 仍按 ID 倒序」。`cd web-next && pnpm vitest run src/pages/Logs.test.tsx` 与 `pnpm typecheck` 通过。
