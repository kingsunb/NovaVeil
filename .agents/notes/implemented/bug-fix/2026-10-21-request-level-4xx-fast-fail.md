# Agent Note: 确定性 4xx 标记与请求级终止演进

Status: implemented

## 问题

NovaVeil 原先把 400/404/422 当作成员级确定性失败: 首个成员失败后仍会按优先级尝试其他成员、Key 与引用链, 直到所有可达叶子都失败一次才终止。超长上下文、请求体结构错误这类拒绝在换渠道后结果不变, 却会把首个真实的 400 埋到后续成员的 401/429 或超时之后, 同时白白消耗请求轮次、冷却等待与上游配额。

opencode2api 最终版在请求级识别确定性拒绝: 只要上游返回 400/422 且正文命中请求级标记, 整个请求立即结束。NovaVeil 需要移植这一语义, 同时保留既有的普通 400 清洗重试, 并维持 401/403/429 的凭据轮换语义。

## 决定

- 判定状态码只接受 400 与 422; 正文标记以 opencode2api `0bb23c7` 的 `isDeterministicClientResponse` 为准: `invalid_request_error`、`invalid_request`、`context_length_exceeded`、`maximum context length`、`string_above_max_length`、`prompt is too long`。413 未包含, 因为上游最终代码没有把它纳入该判定。
- `internal/relay/handler.go` 的错误优先从 `*httpclient.Error.Body` 取上游正文, 没有结构化正文时回退到错误文本; 判定不区分透传与协议转换路径。该标记口径保留下来, 用于识别“清洗也无济于事”的确定性 400。
- 整请求终止已删除: 确定性 400/422 现在与其他确定性请求错误一样, 只排除当前成员并继续尝试下一候选; 全部可达候选失败后才终止, 默认返回统一 400 `暂无可用渠道`, 其中出现过上下文超限时返回固定 400 提示。范围与理由见 [确定性 4xx 改为逐成员排除](2026-10-22-fastfail-per-member-scope.md), 终止文案见 [全组上下文超限时返回明确错误提示](2026-10-22-context-overflow-message.md)。
- 400 且请求体确有可清洗字段时, 每个成员仍执行一次 `sanitizeRequestBody` 并重试; 请求体没有变化时不重放。该成员随后进入确定性排除集合, 本次请求不再重试它。
- 确定性拒绝沿用既有成员失败路径: `recordRouteFailureIfReal` 按 `MemberMaxAttempts` 累积, 达阈值进入冷却; 清会话粘合并设置 `exclude`。终止条件仍是 `len(nonRetryable) >= routableCandidateCount`。
- 401、403、429 不进入该判定。多 Key 渠道的认证拒绝与限流拒绝仍轮换 Key; 无密钥渠道的 401/403 仍按成员级确定性失败处理。

相关历史边界见 [无密钥渠道 401/403 快速失败](2026-09-23-keyless-401-403-deterministic-fast-fail.md) 与 [终止判定分母](2026-09-26-channel-busy-terminal-denominator.md)。

## 备选方案

- **维持请求级整请求终止** — 这是 `d101709` 当初的选择, 能最快返回首个 400; 否掉因为分组成员的模型、窗口和参数能力并不相同, 首个成员拒绝不能证明后续成员也无解, 混合分组会因此丢失可服务候选。
- **直接复用现有 400/404/422 全成员失败路径** — 当初担心它会跨成员、Key 与引用链重放同一个超长请求; 现在通过“每成员只排除一次、全败即终止”控制放大, 因此重新采用该路径, 只额外保留确有字段变化时的清洗重试。
- **把上游 4xx 状态与正文原样透传** — 最强论据是调用方能直接看到上下文超限原因; 否掉因为 NovaVeil 现有下游契约是所有成员不可用统一返回 400 `暂无可用渠道`, 改状态与正文会扩大对外契约面并可能泄漏渠道响应。
- **把 413 一并纳入快速失败** — 最强论据是 opencode2api README 提到 400/413/422; 否掉因为最终代码的判定函数只接受 400/422, 413 也可能来自本地请求体预算而非上游请求级拒绝, 按代码事实不扩张。
- **所有 400 都在清洗后无条件重试一次** — 最强论据是最大限度保留既有清洗兜底; 确定性正文标记命中且请求体无可清洗字段时, 这样会对同一成员多打一次上游, 因此当前只对确有字段被改写的请求重放。

## 后果

- 收益: 确定性 400/422 不再由首个 OpenCode 成员一票否决, 混合分组可以从其他渠道或不同模型/窗口成员成功。
- 代价与已知上限: 全组都拒绝时要等每个可达候选各失败一次才返回统一 400, 失败延迟和上游调用次数随候选数增加; 被拒绝成员按既有规则累计失败并可能冷却。判定仍依赖上游正文标记, 文案变化会退回普通 400 清洗/失败路径。

## 验证

- `internal/relay/deterministic_fastfail_test.go` 覆盖: 标记命中后切换下一成员并成功; 全组确定性 400 时每成员只尝试一次; 单成员清洗重试一次后立即终止; 跨协议转换与普通渠道遵循同一语义; 401/403/429 仍轮换到第二把 Key; 标记表明确排除 413、401、403、429 与 5xx。
