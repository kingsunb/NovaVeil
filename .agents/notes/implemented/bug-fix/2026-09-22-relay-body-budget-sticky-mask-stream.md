# Agent Note: 请求体预算、会话隔离、脱敏表容量与污染流截断

Status: implemented

## 问题

转发路径把并发大包、跨租户同名会话和失败流的成功收尾叠在一起：

1. `readLimitedHTTPRequest` 只有单请求压缩 16MiB、解压 64MiB。全文进请求状态后要到终态才截成 64KiB。脱敏失败直接返回，panic 也不定稿，这两处把全文留在 running 记录里。几个并发满载正文就能把进程内存打满。
2. 粘合和 `sessionUUIDFor` 用裸的 `X-Session-Id` / `x-opencode-session`。不同 API Key 的同名会话粘到同一成员，并共用上游会话号。脱敏键在 `apiKeyID>0` 时已经是 `apiKeyID:sessionKey`，控制台 `api_key_id=0` 却没有前缀，管理员会话名只要写成某个 Key 的隔离键就会共用脱敏表。
3. 脱敏会话表对非空键必入表，未命中也留着，只靠 30 分钟 TTL。
4. 异常 finish 被丢掉之后仍补成功的 `stop` 和 `[DONE]`（Anthropic 是 `end_turn` + `message_stop`，Responses 是 `completed`）。客户端把残缺流当成正常结束。

## 决定

- 进程内请求体共用一把可取消的字节预算，默认 128MiB。读入的压缩字节和解压产出在重叠期间一起计入；压缩缓冲丢弃后只留解压占用。`string(raw.Body)` 是另一份同长度副本，用不等待的 `tryAcquireRelayBodyBudget` 再占一份，避免同一请求拿着第一份额度去等自己。单次预留大于整份预算、或副本放不下时直接 `ErrRelayBodyTooLarge`（HTTP 413）。暂时不够则等待其他请求释放，请求 ctx 取消就返回且不占额度。失败、取消、脱敏失败和 panic 都归还额度。脱敏失败走 `markFailed`；panic 走 `abandonUnfinishedRequest`，已是终态则不改写。两条路径都会把常驻正文截到 64KiB。413 不记成员冷却，和渠道并发槽位满一样只拒绝本次准入，不另建指标。
- 粘合、上游会话号和脱敏共用 `sessionScopeKey`。`apiKeyID>0` 仍是 `apiKeyID:sessionKey`，不把脱敏键剥回原文。`apiKeyID<=0` 加稳定前缀 `console:`，该前缀不以数字开头，不会和数字隔离键相撞。客户端标识仍只读 `X-Session-Id`，没有再用 `x-opencode-session`。不收首条消息、`conversation_id` 或其他头。原文超过 256 字节视为无会话。粘合表单组仍是 4096，跨组合计 16384；满时先清过期，仍满则新会话不建立粘合，已有会话续期不受影响。
- 脱敏会话只有 `Recall` 写出占位符才进入持久表。未命中的临时映射在 `End` 时丢掉，不占条数。持久表上限 4096，超限淘汰最久未访问的一条。已入表的会话在后续未命中时保留并续期，下次命中仍复用占位符。响应侧仍是「这次请求有命中才把映射交给还原」。
- 污染流静默截断，不再调用 `terminalStreamFrames`。服务端仍按失败定稿并计提交后失败。缺哨兵但终止原因合法的完整流（如 MiniMax 不发 `[DONE]`）继续合成正常收尾。

## 备选方案

- **大包在预算里排队直到空出** — 最强理由是不把短暂重叠打成 413，小请求最终也能过。否掉是因为字符串副本的第二笔额度如果等待，会等自己已经拿着的第一笔，请求把自己卡住。永远放不下的单次预留排队也没有意义。
- **粘合继续用裸会话键，只给脱敏加前缀** — 最强理由是粘合表和脱敏表职责不同，少改一条热路径。否掉是因为同名会话仍会粘到同一成员并共用上游会话号，隔离只做了一半。把脱敏键改回裸键则是把已经按 API Key 分开的映射重新并上。
- **未命中也入表，只加条数上限** — 最强理由是实现只加一次淘汰，GetOrCreate 的形状不用动。否掉是因为没有敏感值的请求会把真正需要还原的旧会话挤掉。新的命中必须留下映射，所以超限时淘汰最旧，而不是拒绝这次命中。
- **污染流改成带 error 字段的 stop/[DONE]** — 最强理由是客户端能看到明确错误帧。否掉是因为已开始的 200 流里，成功形态的 stop/[DONE] 会被 SDK 当成完整结束；错误帧又往往不会触发整请求重试。静默截断沿用提交后失败已经在用的做法。

## 后果

- **收益**：并发满载正文有进程级上限；超限、取消、解压失败、脱敏失败和 panic 都会归还额度，后两条还会截断请求状态里的全文。不同 API Key 与控制台的同名会话不再共用粘合、上游会话号和脱敏表。未命中不再撑大脱敏表。污染流不会再被客户端当成成功结束，服务端记账仍是失败。
- **代价与已知上限**：一份 64MiB 正文加上字符串副本正好占满 128MiB，第二份满载正文得到 413。预算不计 sjson 改写时的短命分配。会话键超长或粘合条数已满时，该请求退回普通选路，没有粘合。脱敏表被淘汰的会话下次命中会换新占位符，旧占位符无法再还原。不按「流已断开」重试的客户端会看到截断回答。重访信号：容器内存上限明显偏离 512MiB，或满载正文的双份副本仍把进程打满。

## 验证

- `go test ./internal/relay/ ./internal/relay/mask/` 通过。
- 预算用例覆盖超限拒绝、等待中取消、读中取消、坏 gzip、压缩与解压重叠占用、小请求在剩余额度内放行、字符串副本放不下，以及脱敏失败和 panic 两条路径的额度归还与正文截断。
- 粘合与 `sessionUUIDFor` 用例覆盖不同 API Key、控制台前缀、超长键和跨组条数上限。
- 脱敏表用例覆盖未命中不入表、命中复用、超限淘汰最旧。
- 污染流用例覆盖 OpenAI Chat、Anthropic 和 Responses：下游没有成功终止帧，请求状态为失败。缺 `[DONE]` 的合法完整流仍成功收尾。
