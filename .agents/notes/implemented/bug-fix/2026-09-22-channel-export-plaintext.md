# Agent Note: 渠道文本导出明文名称、地址和密钥

Status: implemented

## 问题

渠道页的「导出全部渠道」要能在另一实例上原样导入。导入格式是一段一个渠道：首行渠道名，第二行上游地址，之后每行一把密钥。导入会拒绝任何含 `****` 的密钥行。导出如果只给掩码，文件不能导回去，管理员还得逐把重填。

列表接口继续只显示掩码。数据库备份里的渠道 Key 与 API Key 另见 [数据库备份导出明文 Key](2026-09-22-backup-export-plaintext-keys.md)。

## 决定

`exportChannel` 写出缓存里的每一个渠道，内置渠道和没有 Key 的渠道都不跳过。每段是明文渠道名、明文 `BaseURL`，然后每行一把明文密钥。没有 Key 时只有名称和地址。多 Key 渠道逐行写 `Keys`，空密钥槽不写；没有多 Key 时回退旧式单 Key。渠道之间空一行。响应不缓存，仍只在管理员会话上提供。

模型清单不写进这份文本。多出来的行会被导入当成密钥。

先前把文本导出改成掩码的决定见 [凭据静态加密与导出脱敏](2026-09-21-credential-at-rest-encryption-and-export-redaction.md)。那篇里数据库备份打码、字段加密和 API Key 长度仍然有效。

## 备选方案

- **继续只导出掩码，让管理员另外点眼睛抄密钥**：能避免文件落地明文，但和导入格式对不上，导出文件不能迁移。渠道页确认框已经告诉管理员文件里是明文。
- **把数据库备份也改回明文**：一份 JSON 会带上 API Key、代理和设置。这次只恢复渠道文本导出，备份仍打码。

## 后果

- **收益**：导出文件可以直接交给渠道导入，名称、地址和密钥都在。
- **代价与已知上限**：导出文件等同于上游凭据，落在管理员的磁盘上。列表、日志和数据库备份不因此带上明文密钥。密钥里如果含换行，会被切成多行，导入时不再是一把密钥。

## 验证

`internal/server/handlers/channel_test.go` 的 `TestFormatChannelExportPlaintextNameURLAndKeys` 断言名称、地址和两把明文 Key 按导入顺序出现，且正文不含 `****`。`TestFormatChannelExportIncludesBuiltinAndKeyless` 断言内置渠道和没有 Key 的渠道仍各占一段。
