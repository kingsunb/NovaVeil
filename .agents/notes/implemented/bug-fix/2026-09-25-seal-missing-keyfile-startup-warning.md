# Agent Note: seal 密钥文件缺失生成新密钥时输出启动告警

Status: implemented

## 问题

`internal/seal` 的 `Configure` 在加密密钥文件（数据目录下 `novaveil-encryption.key`）缺失时直接生成新密钥并以 0600 落盘。该行为对首次部署正确——新装本来没有密钥；但"密钥文件丢失后重启"场景下，同一行为是静默事故：

- 存量 `nv1:` 密文（渠道 Key、多 Key、API Key、自定义头、头模板、JWT 密钥、全局代理等全部密封字段）用旧密钥加密，新密钥一律解不开，`Open` 返回"解密失败, 密钥或数据已损坏"；
- 启动过程无任何提示，故障被推迟到首次解密失败（通常是首个转发请求或首个缓存刷新）才暴露，与换密钥的真实时间点隔了一次重启甚至更久；
- 仓库没有轮换 / re-seal 工具（ROADMAP 未勾选项），旧密文不可恢复时没有自救路径，唯一手段是从备份恢复密钥文件。

docs/modules/storage-secrets.md 的已知边界写明"备份密钥文件是运维义务"，但一条不可观测的义务没有执行信号：运维无从知道该去看备份。

## 决定

生成新密钥成功落盘（hex 写入加 `Chmod 0600`）之后，`resolveKey` 输出一条 WARN 日志（seal.go）：

`seal: 加密密钥文件缺失, 已生成新密钥 %s(权限 0600)。首次部署属正常; 若本实例已有 nv1: 密文数据, 旧凭据将无法解密, 请立即从备份恢复密钥文件`

"这是首次部署（看到属正常）"与"这是密钥丢失（立即恢复备份）"两种语义的区分交给运维按部署历史判断。告警不阻止启动：seal 层无从判断实例是否已有密文数据，而拒绝启动会让正常新装起不来。

## 备选方案

- **启动时扫库检测是否存在 nv1: 密文、有则拒绝启动** — 最强论据是把"密钥丢失"从告警升级为硬阻断，运维不可能漏看；否掉因为 seal 是零业务依赖的底层加密原语包，扫库要求它依赖 db / model 层，反向依赖破坏分层。db 层虽在启动链中先于 `seal.Configure` 初始化，但 `Configure` 必须先于 builtin 补建与 `op.InitCache` 等业务读写执行（cmd/start.go 的注释契约），把数据内容检测塞进密钥解析路径等于让密钥解析依赖业务数据；且拒绝启动在"管理员清库重来"等场景属过度反应。
- **只在文档里强调备份密钥文件** — 最强论据是零代码改动；否掉因为文档救不了静默故障：出事时运维打开的是日志与告警面板，不是部署文档，提示必须出现在出事现场。

## 后果

- **收益**：静默换新密钥成为有日志可查的显式启动事件；密钥丢失场景下故障在启动瞬间暴露并直接指向恢复动作（从备份恢复密钥文件），而非延迟到首次解密失败且无从定位。
- **代价与已知上限**：每次首次部署固定多一条 WARN，属正常噪音——文案首句即自解释；告警本身无法判断实例是否真有存量密文，是否需要行动由运维按部署历史排除。重访信号：轮换 / re-seal 工具落地后，该告警可升级为指向恢复 runbook 的完整指引。

## 验证

- `internal/seal/seal.go` 的 `resolveKey` 在新密钥写盘并 `Chmod` 成功后输出 WARN，文案含文件路径、权限与恢复指引；`cmd/start.go` 在 builtin 补建与缓存刷新之前调用 `seal.Configure`，告警先于任何解密失败出现。
- docs/modules/storage-secrets.md 的已知边界描述该 WARN 语义；轮换 / re-seal 工具仍为 ROADMAP 未勾选项。
