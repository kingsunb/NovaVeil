# Agent Note: 会话与密度缓存生命周期及 sidecar 诊断边界

Status: implemented

## 问题

最近提交的会话缓存和密度落库存在六个相关缺陷：会话时间表永久保存完整输入；同一信号并发初始化或刷新时可能返回不同会话号；切换端点后的旧请求能重新污染密度；清除与写回竞争使旧记录复活；删除模型只清数据库而残留内存值；sidecar（即：Bun 转发辅助进程）的调试日志输出完整鉴权头。

这些问题分别破坏进程内存上限、会话身份稳定性、管理员清除操作与日志安全边界。

## 决定

### 会话时间缓存

- `SessionIDFromSignal` 复用现有带进程盐的 SHA-256（即：固定长度不可逆摘要），时间表只保留 32 字节摘要键，不持有原始消息、系统提示或会话信号。
- `sessionClockStore` 使用标准库 `container/list` 配合映射表；容量与既有消息 ID 缓存一致，为 8192 条；满载时淘汰最早创建的条目。
- 创建时间保留一小时；每次访问清理队首过期或晚于当前时间的条目，命中项也独立检查有效期，防止时钟回拨使队列顺序失真。闲置期间不启动清理协程，缓存始终受容量上限约束。
- 取当前时间、查询、过期清理、创建与返回全部由同一把互斥锁保护；同一信号的并发请求复用同一个胜出的创建时间。

### 密度观测生命周期

- `internal/op/token_density.go` 统一持有密度缓存、采样状态和数据库写入。默认密度、最小样本、前十条平滑校准与每天前三条验证沿用原有规则。
- `TokenDensitySnapshotGet` 返回密度值与绑定当前缓存条目的观测凭据；冷加载同时核对渠道模型存在且 Base URL 与请求目标相同。已删除模型或旧端点不能创建可写观测。
- 每轮请求在 `RequestState.startRound` 进入转发全局锁前取得观测凭据；成功定稿时只向仍属于当前缓存条目的凭据写回。清除前、删除前或切换端点前取得的凭据随后失效。
- 采样写回、单条删除、全部清除、模型删除和端点切换共用 `tokenDensityMu`。写入先成功落库再发布缓存状态；数据库操作失败返回错误并保留原缓存，转发层记录告警。
- 渠道更新和删除按 `channelCacheWriteMu → tokenDensityMu` 顺序加锁，事务成功后在释放密度锁前失效对应条目。模型同步只失效已删除模型，保留模型的有效凭据继续可用。渠道缓存整体刷新失效全部在途观测。
- HTTP 处理器只调用 op 层删除或清除操作，不再单独清理 relay 层缓存。数据库格式和管理 API 格式保持现有契约。

### 诊断日志

`NOVEIL_SIDECAR_DEBUG` 仅在值为 `1` 时启用。Go 端记录目标源站、正文长度和请求头名称；Bun 端记录实际接收的头名。两端都不输出头值；Go 端也不输出 URL 用户信息、路径、查询参数和片段。

- 部分取代 [真实流量校准与密度落库](../feature/2026-11-19-context-token-density-from-upstream-usage.md) 的缓存写入顺序与失效边界；采样规则、路由口径与删除探测页的决定继续有效。
- 在现有 proposed 与 implemented 树中未发现需要一并取代的独立提案；仓库当前没有 rejected 目录。

## 备选方案

- **只给会话表增加容量上限**：改动最少；仍会在容量范围内保留完整的大消息，也不能解决并发创建产生不同时间的问题。
- **在 relay 中保留密度缓存并增加失效回调**：能少移动采样代码；渠道操作与缓存隔着包边界，仍需注册回调及统一锁序，容易遗漏模型自动同步等非 HTTP 入口。
- **只在写回时比较 Base URL**：足以挡住一次端点切换；无法区分清除前后、同名模型重建或端点切回原值后的旧请求。
- **给每个模型单独维护锁与递增版本表**：无关模型可并发落库；还需处理锁对象回收与配置事务的组合锁序。现有每模型每天最多三次稳定期验证，采用统一互斥边界。
- **按敏感头黑名单遮盖日志值**：保留更多诊断信息；自定义认证头不可能穷举，因此日志只保留头名。

## 后果

- 原始会话输入在请求结束后可以释放；缓存有确定容量；管理员清除和渠道变更不会被旧请求撤销。
- 会话缓存超过容量时，最早条目的会话时间需要重新生成；时钟回拨后，无效条目在命中或队首清理时刷新或移除，可能改变受影响会话的标识；未清理的摘要数量不超过 8192。
- 密度采样与配置删除串行，数据库写入期间会阻塞其他密度访问；若数据库延迟成为选路瓶颈，再依据实际延迟评估分片同步。
- 清除或配置变更前已经发出的请求照常完成，但不参与之后的密度学习。持久化失败不会消耗采样计数，后续有效请求可以重试学习。
