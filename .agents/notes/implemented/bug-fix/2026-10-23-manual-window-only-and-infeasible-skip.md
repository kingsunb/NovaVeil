# Agent Note: 仅手动窗口参与选路且请求级不可用成员不冷却

Status: implemented

> 本文接管 [窗口未知的分组成员照常尝试](2026-10-23-context-fit-unknown-window-attempt.md) 中的窗口来源口径；未知手动窗口照常尝试的结论继续有效。

## 问题

同步目录窗口来自上游公开元数据，没有经过本地实测。它此前作为手动窗口缺失时的回退值参与上下文过滤，会把未经确认的目录值变成路由硬限制：目录值偏小会误拒健康成员，目录值偏大又无法提前拦截大请求。产品口径已经明确，只有管理员手动填写的窗口才算限制，同步值只用于界面参考。

同一类误伤也发生在上游拒绝路径。上游 413 只表示本次请求体对当前成员过大，上下文超限的 400/422 也只表示本次输入装不下；两者都不说明成员故障。旧实现把它们送入成员失败记账，达到阈值后会冷却健康成员，导致后续正常大小的请求也失去该候选。

## 决定

### 仅手动窗口参与过滤

`effectiveContextWindow` 只读取 `model_limits[name].context_window` 且要求其大于 0；未填或非正值返回 0，表示窗口未知并照常尝试。`ChannelModel.ContextWindow` 继续同步和展示，但不参与选路。普通选路、引用链扫描和派发前复检共用这一口径，避免三个入口漂移。

本地全量拒绝文案改为说明“手动上下文窗口”，并给出请求估算与最大手动窗口。同步值不进入 `maxCandidateWindow`，也不会因为目录窗口较小而跳过成员。

前端同步区分：手动值仍显示为参与过滤的窗口徽章；只有同步值时显示“同步 N（仅展示）”；两者都没有时显示“未填（不参与过滤）”。探测页明确说明保存的是手动窗口，会成为路由限制。

### 413 与上下文超限只对本次请求跳过

转发循环维护 `infeasibleForRequest`（成员 ID 到 413/400 原因码）。成员命中上游 413，或命中 400/404/422 的上下文超限正文时，只记录本次请求级不可用：清除该成员粘合、归还整链探测占用与紧急额度、加入选路跳过集合并立即换下一候选。该路径不调用 `recordRouteFailureIfReal` 或任何冷却入口。

413 分支位于通用失败记账之前。上下文超限仍先保留既有 400 清洗重试机会，清洗后再次超限才进入请求级跳过，因此 OpenCode developer 角色修正等既有兼容行为不变。

全部可达候选都请求级不可用时按原因终止：含 413 时返回 `413` 与 `请求体超过上游限制（413），请减小上下文后重试`；仅上下文超限时沿用 `400` 与 `请求上下文超出模型上限，请减少输入或提高模型窗口`。若 413 正文同时命中上下文超限关键词，413 文案追加“输入可能超出上游上下文窗口”，状态码仍为 413。普通确定性 400/404/422 继续累计成员失败并冷却，保持原有快速失败语义。

## 备选方案

- **继续让同步窗口作为回退值** — 零配置且能提前拦截明显超限请求；否掉是目录值未经实测，产品已明确它只用于展示，继续参与过滤会重复误拒健康成员。
- **仅同步窗口的成员放到最后尝试** — 保留成员可用性又优先手动窗口；否掉是产品要求所有未填手动窗口的成员按正常优先级照常尝试，不应因元数据缺失降级。
- **把 413 纳入确定性 4xx 并照常计失败** — 实现简单且继续使用逐成员快速失败；否掉是 413 是请求体语义，不是成员健康信号，会让健康成员被后续请求跳过。
- **首个 413 直接终止整个请求** — 最快返回明确错误；否掉是不同成员的上游请求体限制可能不同，立即终止会丢掉仍可承载该请求的健康候选。
- **把 413 加入 `isDeterministicClientResponse`** — 可复用现有判定；否掉是 413 走独立请求级分支，加入该函数会改变其既有契约，并使后续维护者误以为它属于 400/422 的正文标记体系。

## 后果

- **收益**：目录同步不再悄悄改变路由资格；未填手动窗口的成员不会被小目录值误拒。413 与上下文超限不再污染成员健康度，同一请求可继续尝试其它候选，下一个请求也仍会重新评估这些成员。
- **代价与已知上限**：未填手动窗口的大请求会实际打到上游，增加一次可能被拒绝的调用；是否“装得下”完全依赖上游判定。请求级跳过只在单次请求内生效，不做跨请求缓存。混合原因终止时 413 优先于上下文超限与普通确定性 4xx。
- **重访信号**：若大量请求因未填手动窗口反复收到 413，应优先完善探测与批量填写，而不是恢复同步目录值参与过滤。
