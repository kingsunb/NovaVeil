# Agent Note: WARP 出口段冷却改短与轮换死锁修复

Status: implemented

## 问题

2026-10-30 生产事故：NovaVeil 网关对 OpenCode 免费档持续返回 503「WARP 槽位全部不可用，请稍候重试」。该文案出自 NovaVeil 侧 `warpSlotsBusyError`，含义是控制端口拿到的 `/slots` 快照里没有可用槽位；WARP 容器自身在同一时刻返回的 503 正文是 `Service Unavailable`，两者可区分。

根因是 WARP 出口池被自己的冷却与轮换机制锁死，三处缺陷叠加：

- **段冷却把池封死**。被淘汰的 `/64` 段冷却到下一个 UTC 0 点（免费额度重置点），封顶 6 小时。NovaVeil 侧「60 秒窗口内 3 个不同 `/64` 都 429」判定成立时异步调 `POST /rotate?all=1`（见 [槽位账号化与 429 阈值判定](../feature/2026-10-30-warp-slot-account-and-429-quorum.md)），一次换桶把 8 个在岗出口全部淘汰，8 个段同时进冷却，池子清空且在冷却窗口内填不满。段冷却的语义原本是「配额按 UTC 0 点重置，封禁到重置点最省注册配额」，但免费注册的边际成本极低，锁住整池的代价远高于多注册几次。
- **轮换兜底路径不可达**。soft restart 复用旧注册、只换外层源地址，落点常常仍在刚被封禁的段上，被 `claimCandidate` 的冷却检查自我拒绝。放置失败被置为一个新建的 `errors.New` 字符串，而 full re-key 换段兜底的判据是 `errors.Is(err, errEgressPrefixUnchanged)`，两者不相等，换段兜底从不触发，只剩退避重试。
- **池满时无法腾位**。池容量等于槽位数，而 `bindSlotsLocked` 让每个槽位钉住一个出口，`dropIdleLocked` 排除绑着槽位的候选，池满时永远腾不出位置，任何替换都失败。
- **旧段占用不释放**。轮换成功后旧出口直接 `retire`，其段占用标记从不删除，该配额段被永久视为已用，后续注册落到该段即被丢弃。

## 决定

### 冷却改短，不再锁池

`warp.DefaultEgressCooldown` 默认 60 秒。`-cooldown` / `WARP_COOLDOWN` 可调，负值表示段立即可用。删除对齐 UTC 0 点的 `egressCooldownUntil` 与 6 小时封顶的 `maxEgressCooldown`。`Options.EgressCooldown` 零值取默认，负值原样生效。

被封禁的段在冷却窗口内重新注册到同一段会被丢弃重抽，冷却到期自动释放；段冷却仍不跨进程重启保留。

### 轮换链路补齐三处缺口

- 放置失败改用 sentinel `errCannotPlaceRotated`，与 `errEgressPrefixUnchanged` 一起触发 full re-key 换段兜底；换段后仍放不进池用 `errCannotPlaceRekeyed`。soft restart 撞到刚被封禁的段时因此能换段成功，而不是原地退避。
- `dropIdleLocked` 不再排除绑着槽位的空闲出口。槽位在 `bindSlotsLocked` 里重绑，挤掉一个已绑槽位的空闲出口不会丢绑定关系，只会让对应槽位短暂处于 `unknown`。
- `placeRotated` 成功后释放旧出口的段占用，条件是新旧出口落在不同的配额段。同一段时占用标记本就属于新出口，不释放。

### 轮换预算与退避放宽

连续失败的退避从 `300 * 2^n` 秒（封顶 3600 秒）改为 `15 * 2^n` 秒（封顶 300 秒）；单出口 key 每小时轮换上限从 2 次提到 60 次，与全池 full re-key 每小时 60 次同量级。退避只承担防抖，不再承担「别注册太多」。

### 内存上限内置

`-mem-limit` / `WARP_MEM_LIMIT` 默认 `300MiB`。进程启动时 `debug.SetMemoryLimit` 取上限的 80%，让 GC 提前回收；另有 30 秒周期的内存采样，超限只告警不自杀，真正的硬约束由容器的 `--memory=300m` 承担。

## 备选方案

- **保留对齐 UTC 0 点的段冷却** — 最强论据是免费额度按 UTC 0 点重置，封禁到重置点等于零额外注册成本，一次全池换桶不会浪费任何配额。否掉的理由是它把「配额作用域」误当成「资源配额」：段冷却的时间长度与注册成本无关，注册配额本身无上限，而池子空掉的代价是全部请求 503。
- **把全池换桶改成逐槽轮换** — 最强论据是逐槽淘汰能彻底避开「一次清空整池」，NovaVeil 侧的 429 阈值判定也不必触发全池动作。否掉的理由是逐槽轮换仍受段冷却约束：被封禁的段在冷却窗口内换不掉，只要 3 个 `/64` 同时被封，池子照样空；且逐槽轮换的收敛时间更长。先改 WARP 侧的冷却语义，换桶策略是否细化留待观察。
- **用容器 `mem_limit` 代替进程内上限** — 最强论据是容器硬限更可靠，超限即 OOM kill，不需要进程自己判断。否掉的理由是 OOM kill 会直接打断在途请求；进程内软限让 GC 先回收，硬限只在软限失效时才兜底。两层同时启用。
- **把冷却设为 0，彻底不复用被封禁的段** — 最强论据是惩罚最彻底，被 429 的配额段绝不会再被抽到。否掉的理由是同一 `/64` 可能被立刻重新注册命中，惩罚形同虚设，而 60 秒已足够让配额作用域与上游状态脱钩。

## 后果

- **收益**：一次全池换桶不再把池封死；轮换撞到自己刚封禁的段时能换段成功；池满时仍可完成替换；段占用不再无限累积。503 由「全池不可用」降级为「个别槽位短暂不可用」。
- **代价与已知上限**：被封禁的段在冷却窗口内若被重新注册到会被丢弃重抽，冷却时长与上游配额恢复周期不再对齐，短冷却下上游可能仍在限流但段已被复用；此时依赖 NovaVeil 侧 429 阈值判定继续触发换桶。轮换退避与单 key 预算放宽后，注册请求量上升，`registerGap` 12 秒的节奏是实际约束。进程内内存上限是软限，超限只告警，容器硬限缺失时不会自动收缩。
- **状态不持久**：段冷却、段占用、轮换退避仍在进程内存，重启即清零，不能当成跨重启的保证。
