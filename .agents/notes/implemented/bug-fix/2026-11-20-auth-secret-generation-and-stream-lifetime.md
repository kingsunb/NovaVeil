# Agent Note: 登录签名与管理流绑定同代认证状态

Status: implemented

## 问题

管理流只在建立连接时校验 JWT，连接建立后不会因令牌到期、登出或在线改密而结束。登录又把口令验证与读取签名密钥分成两个临界区：旧口令通过验证后，改密可以先完成轮换，登录随后拿到新密钥并签出有效令牌。

在线改密和离线重置持有用户锁，登出持有密钥锁，两种锁无法约束同一密钥的提交与缓存发布顺序；设置重载也可以把较早查询到的密钥覆盖进缓存。

## 决定

- `AuthJWTStateGet` 在 `jwtSecretMu` 内同时取得签名密钥和该代撤销上下文。登出、改密、重置均在该锁内完成数据库提交、缓存发布和旧代撤销；失败保留旧代，成功发布后创建新代。设置重载从读取数据库到发布缓存也使用这把锁，同值重载保留当前代。
- `UserVerifyAndGetJWTSecret` 在用户读锁内验证口令并读取密钥；改密、重置的锁顺序固定为用户锁再密钥锁，持密钥锁的路径不反向获取用户锁。登录使用验证时取得的密钥签名，因此稍后改密只会让该令牌失效，无法让旧口令获得新代令牌。
- `GenerateLoginToken` 负责连接验证与签名；凭据错误由 `ErrInvalidCredentials` 表示，登录接口返回 401 并计入失败次数，密钥存储错误返回 500 并记录服务端日志。
- `VerifyJWTSession` 校验算法、签名、到期时间、签发方和受众，返回到期时间及同一密钥代的撤销上下文。三个管理流均在 `Auth` 后挂 `AuthStream`，将请求上下文绑定到 JWT 到期时间并监听撤销；普通管理请求不注册此回调。
- 流取消时中断阻塞中的响应写出；回调持有解包后的原始响应写入器，并在处理器返回前完成清理，避免访问复用的 Gin 上下文。快照、增量和心跳写出前均检查请求取消，结束时释放订阅、计时器及回调。

## 备选方案

- **每次心跳重新校验 JWT**：容易复用现有验证函数，但撤销存在最长一个心跳周期的延迟，且繁忙流可能持续泄露更新。使用密钥发布时的撤销通知与独立到期计时。
- **所有管理请求都绑定撤销上下文**：入口集中，但改密和登出会取消自身请求上下文，还为短请求引入额外生命周期管理。回调仅应用于三个已知管理流。
- **签名后再校验一次密码或密钥**：能缩短竞争窗口，却仍有校验完成后继续轮换的间隙，并重复执行口令哈希比较。持用户读锁取得验证所属密钥即可建立稳定关系。
- **对所有密钥操作持用户写锁**：可以串行，但每次读取密钥都会阻塞并发凭据验证。保留专用密钥锁，并固定两把锁的获取顺序。

## 后果

旧凭据验证结果无法跨越改密取得新代令牌；数据库、缓存与撤销通知按同一顺序发布。长连接在凭据失效时停止，提交失败不会误踢出当前会话。

密钥读取可能等待改密事务或设置重载，流连接增加到期计时与取消回调。响应已经写入网络缓冲的字节无法撤回，失效时中断后续写出；不支持写入截止时间的内存响应器仅依赖请求上下文退出。

撤销信号和缓存只存在于当前进程；其他实例或离线 `passwd` 写库后，运行中的服务仍需重启以加载新密码和密钥。若支持多实例即时撤销，需要另行设计跨进程通知与缓存一致性，当前改动没有提供该能力。
