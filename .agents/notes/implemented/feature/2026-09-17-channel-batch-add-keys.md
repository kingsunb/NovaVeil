# Agent Note: 渠道批量添加密钥——一行一个密钥的粘贴入口

Status: implemented

## 问题

渠道的多 Key 管理（`Channel.Keys`）此前只能逐把添加：管理员在凭据 Tab 点「添加」逐行填写明文与备注。当上游一次性下发几十把 Key（如采购了一批 sk-* 凭据）时，逐行添加既慢又易漏，且无法从外部文本直接粘贴整批。后端 `normalizeChannelKeys` 本就支持整批 `[]ChannelKey` 整体替换并做唯一性校验，缺的只是前端一个批量入口。

## 决定

在渠道编辑器凭据 Tab 的「上游 Key」分区新增「批量添加」按钮，点击弹出嵌套 `Dialog`：一个多行 `Textarea`，一行一个密钥。确认后按行解析、去首尾空白、丢弃空行、去重，整体追加到 `draft.keys`，复用既有 `buildChannelUpdateRequest` 路径随保存提交。实现集中在 `web-next/src/pages/channels/channel-editor.tsx`：

- `BatchAddKeysDialog` 组件：实时预览「共 N 行 · 可添加 M 个 · 跳过 K 个空行/重复」；每次打开清空上次残留。
- `CredTab` 新增 `batchOpen` 状态与 `existingKeySet`（本会话已输入明文的行集合）作为去重基线传给弹窗。
- 去重只覆盖前端可见明文：空 id 的新行。已保存但仅持掩码的行明文未知，前端无法预判，仍由后端 `normalizeChannelKeys` 的「存在重复密钥」校验兜底（命中则整批替换失败并报错）。

追加的新行 `id` 留空，与单把「添加」按钮产出的行形态一致：后端按 `sha256(Key明文)` 前 8 位生成稳定 id，已保存行（id + 空明文）走 `oldByID` 恢复旧 secret。因此批量添加与逐把添加走完全相同的后端契约，不引入新的接口或字段。

## 备选方案

- **后端新增批量加 Key 接口** — 最强论据是可做服务端去重与原子性；否掉因为前端整批追加复用既有 `keys` 整体替换路径即可，后端 `normalizeChannelKeys` 已做唯一性校验，新增接口只会重复契约、增加维护面。
- **在 Key 列表内联展开一个粘贴区** — 最强论据是无嵌套弹窗、所见即所得；否掉因为密钥列表可能已很长，内联区会挤压已有行、滚动跳变，且粘贴大批量时弹窗的聚焦输入体验更清晰。
- **支持 `key,备注` 逐行解析** — 最强论据是一并导入备注；否掉因为需求明确是「一行一个密钥」，逗号分隔会与含逗号的密钥明文冲突，且备注非批量导入的核心诉求。保持一行一密钥，备注后续在行内单独编辑。

## 后果

- **收益**：批量密钥粘贴即用，几十把 Key 一次导入；前端去重 + 实时计数让用户在提交前看到有效行数与跳过原因，减少无谓的后端报错往返。
- **代价与已知上限**：前端去重无法覆盖「与已保存掩码行明文重复」的情况——这类重复仍由后端兜底报错，整批替换失败需用户手动剔除。重访信号：若用户频繁因「粘贴的 Key 恰好重复某把已存 Key」而整批失败，可考虑在弹窗确认前先拉取该渠道密钥明文做全量去重（代价是额外一次明文请求，需权衡）。
