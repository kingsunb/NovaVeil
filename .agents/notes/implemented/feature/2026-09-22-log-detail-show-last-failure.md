# Agent Note: 日志详情直出最后一次失败详情

Status: implemented

## 问题

日志追踪 Sheet 的「详情」Tab 是面向审计的诊断汇总——把状态、模型、目标、协议链路、中继方式、出口代理、客户端、密钥、脱敏、尝试轮次、各耗时与 token 等键值逐行排开。但请求**失败**时，这份汇总里没有失败原因：`err_class` / `err_brief` 只散落在右列「尝试时间线」的各轮次条目里，或藏在「错误信息」面板的上游原始报错体中，未与顶部的「状态: 失败」同屏出现。要定位一条失败请求的原因，审计者得先看汇总知道「失败了」，再跳到时间线逐轮找最后一次失败的条目。汇总缺了「状态=失败」紧跟「为什么失败」这一环。

## 决定

`web-next/src/pages/Logs.tsx` 的 `DetailTab` 在请求状态为 `failed` 时，紧跟「状态」行之后直出一块「失败详情」：

- **失败原因取「最后一次失败尝试」**：`[...attempts].reverse().find((a) => a.outcome === "failed")`——`attempts` 按轮次升序，倒序取首个 `failed` 即最近一次失败，与右侧时间线「倒序渲染、最新轮次在顶」的口径一致。
- **展示内容**：该尝试的 `err_class`（危险色 Pill，沿用时间线/错误日志的原始分类码，不做本地化映射）与 `err_brief` 全文（`whitespace-pre-wrap`，不设时间线那样的 `line-clamp-2` 截断）；`err_brief` 为空时回退「（无错误摘要）」。
- **渲染条件**：仅当 `req.status === "failed"` 且存在 `outcome === "failed"` 的尝试；`canceled`（已取消）与无失败尝试不渲染，避免把「用户/管理员主动中止」误标成失败原因。

## 备选方案

- **只在时间线/错误面板展示，详情不重复** — 最强论据是信息已存在、避免两处冗余；否掉因为详情 Tab 是审计用的诊断汇总，「状态=失败」与其原因必须同屏，否则定位仍要先记住「失败了」再跳去时间线逐轮排查，汇总的价值打折。
- **把失败原因提升为 `RequestState` 请求级字段（而非从 attempts 里挑）** — 最强论据是前端不必写「挑最后一次失败」的逻辑；否掉因为请求终态失败必然对应最后一次 failed 尝试，`attempts` 已是权威来源，提升字段等于复制同一事实、引入两处需一致维护的契约面。
- **把 `err_class` 映射成中文可读标签** — 最强论据是更友好；否掉因为 `err_class` 是机器口径，全站（时间线、错误日志）统一展示原始码，依赖它可搜索、可对照文档与审计；只在详情里本地化会造成同一条请求两处口径不一致，应先做全局 audit 词汇统一再谈映射。

## 后果

- **收益**：失败请求的诊断汇总里，「状态=失败」下立刻可见最后一次失败分类与摘要，无需再去时间线/错误面板二次定位；测试用 `data-testid="failed-detail"` 钉死渲染与「取最后一次失败而非首次」的语义。
- **代价与已知上限**：纯前端展示改动，不新增后端契约；`err_class` 原始分类码对非开发者不够友好（既有口径，非本次引入）；`err_brief` 为空时只给占位，不额外从上游原始报错体推断摘要——那仍是「错误信息」面板的职责。
- **取代关系**：本篇不取代任何现有笔记，属日志观测面新增；与 [日志实时观测增强（缓存命中率/实时 c/s）](./2026-09-22-log-cache-rate-and-live-output-cps.md) 同域但互不覆盖。
