# Agent Note: 完全渠道透传——一个渠道接受任意客户端协议原样转发

Status: implemented

## 问题

NovaVeil 已有「同协议透传」：客户端协议与渠道协议匹配时（OpenAI 客户端 → OpenAI 渠道）请求体原样转发，不经协议转换，判定在 `supportsNativeFormat()` 按渠道类型 + API 格式硬编码匹配。问题是一个渠道只能透传自身协议；若上游是多协议网关（如 OpenRouter、自建反代）同时支持 OpenAI Chat、Anthropic Messages、图片、语音等接口，当前架构需为每种协议建独立渠道，且跨协议请求仍走转换管线。后端已实现，前端待补。

## 决定

新增「完全渠道透传」开关，启用后该渠道接受任意客户端协议，请求体、URL 路径、响应体全部原样透传至上游，不做任何协议转换。参考 [new-api](https://github.com/QuantumNous/new-api) 的两级开关设计：

- 全局 `PassThroughRequestEnabled`（默认 `false`）
- 渠道级 `PassThroughBodyEnabled`（默认 `false`）

任一为 `true` 即启用透传。**完全透传不跳过分组路由**：请求仍经过 提取 model → 查分组 → 选渠道（含 failover、Key 轮询）→ 透传至上游。「完全」指任意协议都原样转发，不是绕过路由。设计文档见 [docs/CHANNEL_PASSTHROUGH.md](../../../../docs/CHANNEL_PASSTHROUGH.md)。

## 备选方案

- **为每种协议建独立渠道** — 最强论据是无需新代码、复用现有同协议透传；否掉因为多协议上游的渠道数量随协议数线性膨胀，运维成本高，且跨协议请求仍会走转换管线，没解决根本问题。
- **完全绕过路由直连上游** — 最强论据是路径最短、延迟最低；否掉因为丢失 failover、Key 轮询、计费、用量统计与审计，这些是网关的核心价值，透传不能以放弃路由为代价。
- **仅扩 `supportsNativeFormat()` 硬编码匹配表** — 最强论据是改动最小；否掉因为每新增一种协议都要改代码重新发布，无法运行时配置，且硬编码表无法表达「这个渠道就是任意协议都透传」的意图。

## 后果

- **收益**：一个渠道服务多协议上游，渠道数量不再随协议膨胀；运行时开关，无需改代码；仍保留路由/failover/Key 轮询/计费。
- **代价与已知上限**：透传渠道不做协议转换，用量提取与计费依赖上游响应格式可解析；前端管理 UI 待补（见设计文档 §5.5）。重访信号：上游响应格式无法提取用量导致计费缺失时，需在透传与转换之间补一个「仅转换响应、不转换请求」的中间档。
