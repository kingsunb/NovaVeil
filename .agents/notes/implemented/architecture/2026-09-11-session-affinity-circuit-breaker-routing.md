# Agent Note: 会话粘合 + 三态熔断 + 非阻塞半开探测的路由架构

Status: implemented

## 问题

多渠道 failover 下，同一会话的连续请求可能落到不同渠道，破坏多轮上下文一致性（部分上游按渠道隔离会话状态）。同时渠道故障需要冷却恢复，但恢复探测不能阻塞正常流量，全部渠道不可用时要有自愈路径。这是请求路由的核心流程，权威文档见 [docs/DEVELOPMENT_routing.md](../../../docs/DEVELOPMENT_routing.md)。

## 决定

路由由三个机制组合：

1. **会话粘合**：按 `X-Session-Id` 把会话绑定到渠道。粘合未过期且目标渠道为 CLOSED 时，优先走粘合渠道；粘合渠道请求失败且还有重试次数则重试粘合渠道，否则渠道进 OPEN、算冷却、清粘合，从渠道 1 重新扫描。粘合渠道成功则刷新粘合时间。
2. **三态熔断**：渠道状态 CLOSED（正常）/ OPEN（冷却中，跳过）/ HALF_OPEN（探测中）。扫描时跳过 OPEN 与 HALF_OPEN。
3. **非阻塞半开探测**：存在正常（CLOSED）渠道时，半开探测不阻塞主路径；全部不可用时从渠道 1 重新扫描触发恢复。

## 备选方案

- **无粘合纯轮询/加权选择** — 最强论据是实现最简、负载最均；否掉因为多轮上下文会跨渠道断裂，上游按渠道隔离会话状态时直接破坏对话连续性，这是网关场景下的真实痛点。
- **由客户端指定渠道** — 最强论据是精确可控；否掉因为向客户端泄露渠道细节、破坏渠道抽象，且失去服务端 failover 与 Key 轮询能力，客户端不该承担路由决策。
- **熔断只用 CLOSED/OPEN 二态，无半开** — 最强论据是状态机更简；否掉因为恢复时无探测，要么冷却到期直接全量放行（洪峰打满刚恢复的渠道再次熔断），要么永不恢复（需人工介入）。半开探测以受控流量验证恢复。

## 后果

- **收益**：会话内多轮上下文一致；渠道故障自动冷却与自愈；半开探测不阻塞正常流量，恢复以受控流量渐进。
- **代价与已知上限**：粘合渠道故障时仍需重试与清粘合逻辑，路由状态机复杂度上升；半开探测的并发边界（探测请求与正常请求的竞态）需测试守死。重访信号：上游不再按渠道隔离会话状态时粘合可简化；渠道数量很大时扫描 + 半开探测的调度需评估开销。
