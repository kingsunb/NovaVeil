# Agent Note: 会话粘合 + 三态熔断 + 非阻塞半开探测的路由架构

Status: implemented

## 问题

多渠道 failover 下，同一会话的连续请求可能落到不同渠道，破坏多轮上下文一致性（部分上游按渠道隔离会话状态）。同时渠道故障需要冷却恢复，但恢复探测不能阻塞正常流量，全部渠道不可用时要有自愈路径。这是请求路由的核心流程，权威文档见 [docs/DEVELOPMENT_routing.md](../../../../docs/DEVELOPMENT_routing.md)。

## 决定

路由由三个机制组合：

1. **会话粘合**：客户端标识仍只来自 `X-Session-Id`，没有时用 `x-opencode-session`。表键是按 API Key 隔离后的 `sessionScopeKey`，不是裸会话名。详见 [请求体预算、会话隔离与污染流截断](../bug-fix/2026-09-22-relay-body-budget-sticky-mask-stream.md)。粘合未过期且目标渠道为 CLOSED 时，优先走粘合渠道；粘合渠道请求失败且还有重试次数则重试粘合渠道，否则渠道进 OPEN、算冷却、清粘合，从渠道 1 重新扫描。粘合渠道成功则刷新粘合时间。
2. **三态熔断**：渠道状态 CLOSED（正常）/ OPEN（冷却中，跳过）/ HALF_OPEN（探测中）。扫描时跳过 OPEN 与 HALF_OPEN。
3. **非阻塞半开探测**：存在正常（CLOSED）渠道时，半开探测不阻塞主路径；全部不可用时从渠道 1 重新扫描触发恢复。

成员重试间隔 `member_retry_interval_seconds` 使用非负小数秒，`0` 表示立即重试，`0.01` 表示 10 毫秒；新分组仍默认 2 秒。API、JSON 配置与等待函数都保留小数，转换到 `time.Duration` 前先乘纳秒单位，避免把亚秒间隔截成 0。已有整数 JSON 直接兼容，v7 旧整数列迁移显式转成 `float64`。整份零值配置继续回填默认；正常完整配置中的显式 0 保留。

重试间隔为 0 只消除成员失败后的等待。无候选、损坏引用反复跳过以及渠道或模型失效时，重新选路仍使用默认 2 秒退避，给配置修复与冷却恢复留出窗口；正间隔继续按配置执行。该参数不改变成员尝试上限、冷却、请求轮次预算和取消语义。

## 备选方案

- **无粘合纯轮询/加权选择** — 最强论据是实现最简、负载最均；否掉因为多轮上下文会跨渠道断裂，上游按渠道隔离会话状态时直接破坏对话连续性，这是网关场景下的真实痛点。
- **由客户端指定渠道** — 最强论据是精确可控；否掉因为向客户端泄露渠道细节、破坏渠道抽象，且失去服务端 failover 与 Key 轮询能力，客户端不该承担路由决策。
- **熔断只用 CLOSED/OPEN 二态，无半开** — 最强论据是状态机更简；否掉因为恢复时无探测，要么冷却到期直接全量放行（洪峰打满刚恢复的渠道再次熔断），要么永不恢复（需人工介入）。半开探测以受控流量验证恢复。
- **新增毫秒字段保存精细间隔** — 整数毫秒便于直接计算，但需要兼容两套配置字段并处理优先级；已有秒字段改为小数能保留界面、JSON 字段名和旧整数值，避免双重配置来源。
- **所有等待直接共用零间隔** — 调用点最少，但无候选或多个损坏引用会紧循环，在上游恢复前耗尽请求轮次；无目标时保留独立退避，真实成员重试仍尊重 0。

## 后果

- **收益**：会话内多轮上下文一致；渠道故障自动冷却与自愈；半开探测不阻塞正常流量，恢复以受控流量渐进。
- **代价与已知上限**：粘合渠道故障时仍需重试与清粘合逻辑，路由状态机复杂度上升；半开探测的并发边界（探测请求与正常请求的竞态）需测试守死。重访信号：上游不再按渠道隔离会话状态时粘合可简化；渠道数量很大时扫描 + 半开探测的调度需评估开销。
- **重试间隔**：管理员可以按需直接重试或设置亚秒等待；0 与较小间隔会增加短时重试频率，次数限制与冷却仍负责收敛。写入小数后旧版后端的整数解码器无法读取，降级前需把间隔改回整数；无候选等待的默认退避与真实成员重试必须保持区分。
