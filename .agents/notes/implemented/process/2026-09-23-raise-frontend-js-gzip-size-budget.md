# Agent Note: 前端 JS gzip 体积预算 250→256 KB

Status: implemented

## 问题

`web-next-ci` 的 `bundle` job（`pnpm size`）在 main 推送后失败：`size-limit` 实测「JS 总和 (gzip)」= 250.03 kB，超 `.size-limit.json` 的 250 KB 门槛 30 字节。2026-09-18 全量审计早已记录 245.6 kB / 250 kB = 98.3%「余量不足」；2026-09-22 落地的日志实时观测（缓存命中率、流式 c/s）与登录「信任此设备」等功能增量把总量顶过线。超线来自**真实功能增长**（Logs chunk 63.19→63.91 kB 等），不是意外引入的依赖或冗余。

## 决定

`.size-limit.json` 的「JS 总和 (gzip)」门槛 = `256 KB`，给当前功能面留约 6 KB 余量；「JS 单 chunk (gzip)」150 KB 与「CSS (gzip)」14 KB 门槛不变，仍有余量。预算的意义是**抓意外膨胀**，不是冻结在当前功能面：本次超线是已评审功能的正当代价，故对齐预算而非删功能。

## 备选方案

- **瘦身源码压回 250 KB 内** — 否。30 字节 gzip 赤字只能靠删真实 UX 文案/逻辑换回，得不偿失，且功能面再进一步又会顶线。
- **一次性抬到 260 KB 或更高** — 否。过度放宽会让门槛失去捕捉意外膨胀的灵敏度，256 已覆盖本次增量并留小缓冲。
- **路由级按需加载 / 按页拆 chunk** — 长期正解，但属独立重构、改动面大，不与本次预算对齐捆绑；记为下方重访信号。

## 后果

- **收益**：main 推送恢复；预算与当前功能面对齐。
- **代价**：上限放宽 6 KB，报「意外膨胀」的提前量略降，仍属整块量级、远小于真实泄漏风险。
- **重访信号**：下次逼近 256 KB 时，先做路由级 code-splitting 或按页拆 chunk，停止单纯抬数值；2026-09-18 全量审计的「余量不足」为同源提醒。

## 验证

- `cd web-next && pnpm size` 通过（JS 总和 250.03 kB < 256 KB）。
- `pnpm verify-notes` 通过。
