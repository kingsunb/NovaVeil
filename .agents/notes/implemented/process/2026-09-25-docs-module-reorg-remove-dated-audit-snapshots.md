# Agent Note: 文档按主模块重组并移除日期命名的过程性审计快照

Status: implemented

## 问题

docs/ 里沉淀了两类互相矛盾的文档：一类是按主模块组织的**事实**文档（部署、路由、脱敏），另一类是带日期的**过程快照**——5 份审计（问题清单 → 全面审计 → 跟进 → 验证 → 修复摘要）与 2 份头部已自注"已落地，与代码不一致时以代码为准"的计划书。审计快照形成于 09-13 至 09-21，其中大部分条目经 09-21 修复批次闭环，但仍开放的问题与已接受的风险**没有一处按主题归档**——读者必须通读五份带日期的文档并自己做时间线推理，才能知道某模块现在的真实边界。这是 docs/README.md 自己定义的「事实与因果分离」的反面：docs 该回答"当前怎么运转 + 当前边界在哪"，而审计文档回答的是"某天的检查发现了什么"。

同时仓库缺少模块级总览：`DEVELOPMENT_routing.md` 只覆盖路由一个主题，relay 的协议互转 / 透传 / bodylimit / 可视化、seal 加密、eval 队列、自更新、构建链等主题散落在 Agent Notes 与源码注释里，没有一个"这个模块怎么做的、当时怎么想的"的入口。

## 决定

**移除全部日期命名的审计快照与已落地计划书，闭环状态并入主题文档；新建 `docs/modules/` 九篇按主模块组织的实现说明。** git 历史保留全部原文，不迁移内容到新文档。

- 删除 `docs/audits/` 整目录（2026-09-13 问题清单、09-18 全面审计、09-20 跟进审计、09-20 验证报告、09-21 修复摘要共 5 份）。仍开放的问题（X-Forwarded-Proto 信任、限速桶塌陷、SSRF 出口回退等）已经在 ROADMAP 有未勾选项，把审计新发现且 ROADMAP 没有的项（提交后流失败泄漏探测占用）补进 ROADMAP 未勾选清单；各模块的结构性边界（seal 无轮换、迁移无互斥、CI 无 -race 等）写入对应模块文档的「已知边界」节。
- 删除 `OPENCODE_NATIVE_PROTOCOL_PLAN.md` 与 `OPENCODE_SESSION_CACHE_KEY_PLAN.md`：两项都已落地，因果与备选完整保留在对应 Agent Note（`2026-09-22-opencode-upstream-protocol`、`2026-09-22-opencode-session-and-prompt-cache-key`），现在时事实并入 `modules/relay.md`。保留 `OPENCODE_MODEL_CAPABILITY_PLAN.md`（仍未实施，且修正其对已删计划书的链接指向 modules/relay.md）。
- 保留 `frontend-redesign/` 两份：FOLLOW_UP 的 P1/P2 验收项与 ROUTE_TRANSITION 的 P1/P2 性能项仍是真实待办，不是已落地事实。
- 新建 `docs/modules/`：relay（转发引擎）、server-auth（HTTP 与鉴权）、mask（脱敏）、storage-secrets（数据与凭据）、eval（模型评估）、task-limits（任务与限流）、update（自更新）、web-next（前端控制台）、build-ci（构建与 CI）。每篇统一四节结构：**怎么做的**（现在时事实，含关键文件与函数名）、**设计想法**（当时为什么这么定，链接因果 Agent Note）、**已知边界**（含未修复缺陷的有意标注）、**深入阅读**（主题权威文档与笔记入口）。与主题权威文档（DEVELOPMENT_routing、脱敏开发系列）做链接而不是复制，modules 是总览层，权威细节仍在原文档。
- `docs/README.md` 重写为分节索引：从这里开始 → 主模块实现 → 部署与运维 → 脱敏开发 → 前端重设计 → 审计报告（一句"已移除，见 git 历史"的指引，不留空表）。

## 备选方案

### 为什么不保留审计文档加"已闭环"标记？

闭环状态会随修复漂移：标记一旦过时比没有标记更误导（读者会信"仍开放"的假阴性或"已修"的假阳性）。过程文档的正确归宿是 git 历史与 Agent Note 的因果记录，不是在 docs/ 里养老。ROADMAP 的未勾选项 + 模块文档的「已知边界」已经覆盖"当前还有什么没修"这一全部信息需求。

### 为什么不把审计内容全文并入新文档？

审计原文 85KB，大部分是已修复条目的 file:line 证据，对当前读者是噪音；逐条"已修复"状态会随代码演进失效。只迁移**仍然成立的事实**（机制描述）与**仍开放的边界**（缺陷、回退决策），已修复过程的完整因果本来就在 Agent Notes 与 git 提交里。

### 为什么不按生命周期（deploy/dev/audit）组织 docs/？

按生命周期组织适合过程归档，按主题组织适合事实查询——"这个模块怎么做的、边界在哪"是高频问题，"09-20 那次审计说了什么"是低频考古。主题树（modules + 专题权威文档）加 README 分节索引已能覆盖两类查询，不引入第二棵树。

### 为什么不归档而不是删除？

`pnpm archive-agent-note` 的归档机制只服务于 Agent Notes（lifecycle 目录 + manifest 封印），docs/ 没有对应机制；docs 的"归档"语义就是 git 历史。保留一份永不更新的死文档在活跃目录里，只会让 `check-anchors` 与读者都困惑。

## 后果

**收益**：docs/ 全部为现在时事实或明确标注的待办；按模块 5 分钟能定位一个机制的实现文件与设计理由；审计发现的未修项有了唯一权威去处（ROADMAP 未勾选 + 模块文档已知边界）；新文档把散落的"设计想法"（非阻塞半开、fail-closed 脱敏、限速 fail-close 等）从 Notes 与注释里提炼成可读的动机段落。

**代价**：审计报告失去"在 docs 里直接翻阅"的便利（git show 仍可取）；"哪个问题哪天发现的"这类时间线信息只在 git 历史与 Note 日期里，不在活跃文档；9 篇新文档是一次性写入的实现快照，代码演进后**必须**随手更新对应模块文档（约定不变：docs 写事实，变了就改，不追加流水账）。删除的是 5+2 份已跟踪文件，任何基于旧路径的外部链接会 404。

**验证**：`pnpm verify-notes` 通过（59 篇）；全仓无对已删路径的残留引用；9 篇模块文档对 `.agents/notes/` 的 7 个链接逐一核对真实存在；`docs/README.md` 全部相对链接指向存在的文件。
